# Callback Functions

---

## Functions as First-Class Citizens

In JavaScript, functions are **first-class citizens** — meaning they can be treated like any other value. This is true for three reasons:

1. A function can be **assigned to a variable**
2. A function can be **passed as an argument** to another function
3. A function can be **returned** from another function

Callbacks are all about the second point — passing a function as an argument.

---

## What is a Callback Function?

A **callback function** is a function that is passed as an argument to another function.

```js
function a(wrapper) {
  console.log('Hello');
  wrapper(); // calling the passed-in function
}

function b() {
  console.log('Bye');
}

a(b); // b is the callback function
// Hello
// Bye
```

Here, `b` is passed as an argument to `a`. Inside `a`, it is received as the parameter `wrapper` and then called. Because `b` is being passed as an argument into another function, `b` is a **callback function**.

> **Key rule:** The execution of a callback function depends on the function it is passed to. If `a` is never called, `b` is never called either — unless you call `b` explicitly elsewhere.

---

## Why Callbacks? — Asynchronous JavaScript

Callbacks become essential when dealing with **asynchronous operations** — things that happen later, not immediately. Examples include:

- Waiting for a timer to expire
- Waiting for data to come back from a server
- Waiting for the user to interact with the page

JavaScript is a **single-threaded, synchronous** language — it executes code line by line. It cannot simply stop and wait for a slow operation. Instead, the async operation is registered, and when it completes, a callback function is called to handle the result.

---

### Example 1 — `setTimeout`

```js
setTimeout(function callback() {
  console.log('Executed after a delay');
}, 4000);

console.log('Hello');

// Output:
// Hello
// Executed after a delay  (after 4 seconds)
```

**What happens under the hood:**

1. JavaScript encounters `setTimeout` and registers the callback function in the browser's timer API, along with the 4-second delay.
2. JavaScript does not wait — it immediately moves to the next line and logs `'Hello'`.
3. After 4 seconds, the timer expires. The callback is pushed onto the call stack and executed.
4. The function is "called back" — that is why it is called a callback function.

---

### Example 2 — Fetching Data from an API

```js
fetch(url)
  .then(function callback(response) {
    console.log(response);
  });
```

**What happens:**

1. JavaScript sends a request to the server.
2. The callback function is not executed immediately — it is registered and stored.
3. Whenever the server responds (instantly or after several seconds, depending on traffic), the callback is called with the response.
4. The execution of the callback depends entirely on when the response arrives — that is an async operation.

---

### Example 3 — DOM Events

```js
const button = document.getElementById('button');

button.addEventListener('click', function callback() {
  console.log('clicked');
});
```

The callback is only executed when the button is actually clicked. If the event never fires, the function never runs. Again, execution depends on an external action — making this an async operation handled by a callback.

## Uses of Callbacks

### 1. Handling Asynchronous Operations

The most common use — callbacks run after an async task completes:

- API requests (fetching data from a server)
- Reading files (Node.js file system)
- Event listeners (clicks, keyboard inputs)
- Database queries (retrieving data)
- Timers (`setTimeout`, `setInterval`)

### 2. Higher-Order Functions

When a function needs to behave differently based on input, callbacks make it flexible. A **higher-order function** is one that accepts another function as an argument:

```js
function calculate(a, b, callback) {
  return callback(a, b);
}

function add(x, y) {
  return x + y;
}

function multiply(x, y) {
  return x * y;
}

console.log(calculate(5, 3, add));      // 8
console.log(calculate(5, 3, multiply)); // 15
```

The same `calculate` function produces different results depending on which callback is passed in.

### 3. Event Listeners

JavaScript is event-driven — callbacks handle user interactions:

```js
document.getElementById('myButton').addEventListener('click', function () {
  console.log('Button clicked!');
});
```

The anonymous function is a callback that only runs when the button is clicked.

### 4. API Calls

Callbacks are useful when processing data retrieved from an API:

```js
function fetchData(callback) {
  fetch('https://jsonplaceholder.typicode.com/todos/1')
    .then((response) => response.json())
    .then((data) => callback(data))
    .catch((error) => console.error('Error:', error));
}

function handleData(data) {
  console.log('Fetched Data:', data);
}

fetchData(handleData);
```

`fetchData()` retrieves the data and passes it to `handleData()` for processing.

## Error Handling in Callbacks

The standard Node.js convention for callbacks is the **error-first pattern** — the first argument is always the error (or `null` if there is none), and the second is the result:

```js
function divide(a, b, callback) {
  if (b === 0) {
    callback(new Error('Cannot divide by zero'), null);
  } else {
    callback(null, a / b);
  }
}

function handleResult(error, result) {
  if (error) {
    console.log('Error:', error.message);
  } else {
    console.log('Result:', result);
  }
}

divide(10, 2, handleResult); // Result: 5
divide(10, 0, handleResult); // Error: Cannot divide by zero
```

This works for single operations, but when callbacks are deeply nested, handling errors at every level becomes messy and repetitive — one of the key reasons to prefer Promises.

---

Callbacks are useful, but they come with two significant problems when used for multiple chained async operations.

---

### Problem 1 — Callback Hell (Pyramid of Doom)

In real applications, async operations often depend on each other. Consider a hotel booking flow where each step depends on the previous one:

1. BookApp hotel
2. Proceed to payment (only if hotel is booked)
3. Show booking status (only if payment succeeds)
4. Update booking history (only if status is shown)

Each step calls an API. Each API returns a response. Each response needs a callback to handle it. When you have error handling at each level too, the nesting looks like this:

```js
bookHotel(hotelId, function (error, bookingResult) {
  if (error) {
    handleError(error);
  } else {
    proceedToPayment(hotelId, amount, function (error, paymentResult) {
      if (error) {
        handleError(error);
      } else {
        showBookingStatus(bookingResult, function (error, status) {
          if (error) {
            handleError(error);
          } else {
            updateBookingHistory(status, function (error, result) {
              if (error) {
                handleError(error);
              } else {
                // finally done
                console.log('Booking complete');
              }
            });
          }
        });
      }
    });
  }
});
```

The shape of the code — each callback indented further than the last — is why this is called the **Pyramid of Doom**:

```
bookHotel(
    proceedToPayment(
        showBookingStatus(
            updateBookingHistory(
                // deep inside here
            )
        )
    )
)
```

Code should grow **vertically** (downward). Callback hell makes code grow **horizontally** (rightward). This causes real problems:

- Hard to read and understand
- Hard to manage and maintain
- Hard to debug — tracking down an error buried inside four levels of nesting is painful
- Hard for other developers to work with

---

### Problem 2 — Inversion of Control

When you pass a callback into a function, you hand over the **control of execution** of that callback to the outer function. The outer function decides if and when your callback runs. This is called **inversion of control**.

```js
bookHotel(hotelId, proceedToPayment);
//                  ^
//   you have given control of proceedToPayment
//   to bookHotel — it decides when to call it
```

In normal code, you call your own functions when you want. With callbacks, you give up that control.

This becomes a problem when:
- The server is down or idle — the callback never runs
- The API takes too long — your entire flow is stalled
- A third-party library has a bug and never calls your callback
- You have no way to guarantee your code will execute

```js
// The execution of proceedToPayment depends entirely
// on bookHotel finishing — if bookHotel gets stuck,
// proceedToPayment never runs, and neither does anything after it.
bookHotel(hotelId, proceedToPayment);
```

You have handed the keys to someone else.

---

## Callbacks vs Promises

These two problems — callback hell and inversion of control — are exactly what **Promises** were designed to solve:

| Problem | Callbacks | Promises |
|---|---|---|
| Code structure | Grows horizontally (Pyramid of Doom) | Grows vertically (flat chain) |
| Inversion of control | You hand over execution control | You attach handlers yourself |
| Error handling | Must handle at every nested level | Single `.catch()` at the end |
| Readability | Difficult with many steps | Clean and readable |

```js
// Callback hell (horizontal)
bookHotel(id, (err, result) => {
  proceedToPayment(result, (err, payment) => {
    showBookingStatus(payment, (err, status) => {
      updateBookingHistory(status, () => { ... });
    });
  });
});

// Promise chain (vertical — clean)
bookHotel(id)
  .then((result) => proceedToPayment(result))
  .then((payment) => showBookingStatus(payment))
  .then((status) => updateBookingHistory(status))
  .catch((error) => handleError(error));
```

## Solutions to Callback Hell

### 1. Modularize — Name and Extract Functions

Instead of writing anonymous callbacks inline, extract each step into a named function. This flattens the nesting without changing the logic:

```js
function step1(callback) {
  setTimeout(() => {
    console.log('Step 1 completed');
    callback();
  }, 1000);
}

function step2(callback) {
  setTimeout(() => {
    console.log('Step 2 completed');
    callback();
  }, 1000);
}

function step3(callback) {
  setTimeout(() => {
    console.log('Step 3 completed');
    callback();
  }, 1000);
}

// Still callbacks, but named and readable
step1(() => {
  step2(() => {
    step3(() => {
      console.log('All steps completed');
    });
  });
});
```

This helps readability but doesn't eliminate nesting for deeply sequential flows.

### 2. Promises

Promises eliminate nesting entirely by chaining `.then()` calls vertically:

```js
function step1() {
  return new Promise((resolve) => {
    setTimeout(() => {
      console.log('Step 1 completed');
      resolve();
    }, 1000);
  });
}

function step2() {
  return new Promise((resolve) => {
    setTimeout(() => {
      console.log('Step 2 completed');
      resolve();
    }, 1000);
  });
}

function step3() {
  return new Promise((resolve) => {
    setTimeout(() => {
      console.log('Step 3 completed');
      resolve();
    }, 1000);
  });
}

step1()
  .then(step2)
  .then(step3)
  .then(() => console.log('All steps completed'))
  .catch((error) => console.error(error));
```

A single `.catch()` at the end handles errors from any step in the chain.

For more complex data pipelines, the same pattern applies cleanly:

```js
getDataFromAPI()
  .then(parseData)
  .then(processData)
  .then(saveData)
  .then(sendEmail)
  .then((response) => console.log('Done:', response))
  .catch((error) => console.error('Error:', error));
```

### 3. `async`/`await`

`async`/`await` makes async code look and read like synchronous code — the cleanest solution:

```js
async function processSteps() {
  await step1();
  await step2();
  await step3();
  console.log('All steps completed');
}

processSteps();
```

With error handling:

```js
async function handleData() {
  try {
    const data = await getDataFromAPI();
    const parsedData = await parseData(data);
    const processedData = await processData(parsedData);
    const savedData = await saveData(processedData);
    const response = await sendEmail(savedData);
    console.log('Done:', response);
  } catch (error) {
    console.error('Error:', error);
  }
}

handleData();
```

Each step is a single line. The `try...catch` block handles all errors in one place.

## When to Use Callbacks

**Use callbacks when:**
- Handling async tasks with a simple, single-level response (timers, event listeners)
- Implementing event-driven programming
- Building higher-order functions that need flexible behavior (like `calculate(a, b, add)`)
- Working with APIs or libraries that already use the callback pattern

**Avoid callbacks when:**
- Multiple async operations depend on each other — use Promises or `async`/`await` instead
- Code becomes nested and unreadable (Pyramid of Doom)
- You need centralized error handling — Promises handle this with a single `.catch()`

---

## Summary

A **callback function** is a function passed as an argument to another function, to be called at a later point — usually when an async operation completes.

- Used with timers (`setTimeout`), API requests (`fetch`), DOM events (`addEventListener`), and higher-order functions
- The execution of a callback depends on the function it is passed to
- The **error-first pattern** `(error, result)` is the standard Node.js convention for callback-based error handling
- **Callback hell** occurs when callbacks nest inside callbacks, making code grow horizontally and become hard to manage
- **Inversion of control** occurs when you lose control of when your own function runs by handing it to an external function
- **Solutions:** extract named functions to reduce nesting; use **Promises** to chain vertically; use **`async`/`await`** for the cleanest, most readable code
- Use callbacks for simple single-level async tasks and event-driven programming; avoid them when multiple operations depend on each other
