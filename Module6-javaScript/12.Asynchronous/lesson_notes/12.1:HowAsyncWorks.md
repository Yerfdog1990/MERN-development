# How Async JavaScript Works 

---

## 1. JavaScript's Core Nature

By definition, **JavaScript is a single-threaded, synchronous language**.

| Term | Meaning |
|---|---|
| **Single-threaded** | Executes one thing at a time — one line, one function, sequentially |
| **Synchronous** | Executes code line by line, in order — never jumps from line 3 to line 50 and back |

### How Synchronous Execution Works

```javascript
function hello() {
  console.log("Hello");
}

hello();
console.log("Bye bye");
```

**Execution flow:**
1. Browser creates a **Global Execution Context (GEC)** and pushes it onto the **Call Stack**
2. `hello()` is called → a **Function Execution Context** is created and pushed onto the call stack
3. `console.log("Hello")` runs → outputs `Hello`
4. Function execution context is **removed** from the call stack
5. `console.log("Bye bye")` runs → outputs `Bye bye`
6. GEC is removed from the call stack

**Output:**
```
Hello
Bye bye
```

> Everything runs **top to bottom, one at a time** — this is synchronous behavior.

---

## 2. What is Asynchronous JavaScript?

In async JavaScript, **a piece of code is divided into multiple chunks**:

- Some chunks execute **now** (when called)
- Some chunks execute **later** (when a condition is met — a timer expires, a server responds, a user clicks a button, etc.)

### Real-world Examples of Async Triggers

| Async Trigger | Example |
|---|---|
| **Time delay** | Show a loader for 3 seconds before navigating |
| **API/server response** | Fetch product data from a database |
| **User interaction** | Click a button to add a product to a cart |
| **User input** | Searching for "Nike shoes" on an e-commerce site |

### Why Async Is Necessary

```javascript
// PROBLEM: Synchronous wait blocks everything
console.log("Let's begin");
// Imagine waiting 4 seconds here...
// The entire browser UI freezes — no clicks, no interactions possible!
console.log("Let's wait");
console.log("Bye bye");
```

If JavaScript waited synchronously for 4 seconds, **the entire browser UI would freeze** — no buttons work, nothing responds. Users would leave the page immediately.

> **Async solves this** — JavaScript hands off the waiting task and keeps running other code.

## 3. What JavaScript Engine Actually Contains

A common misconception is that JavaScript handles everything. In reality:

### Inside the JavaScript Engine
- Only the **Call Stack**
- Creates and manages **Execution Contexts**

### What the Browser Provides (NOT the JS Engine)

The **browser** is a larger environment that wraps the JS engine and provides:

```
┌─────────────────────────────────────────────────────────────┐
│                         BROWSER                             │
│                                                             │
│   ┌──────────────────┐    ┌─────────────────────────────┐   │
│   │  JavaScript      │    │        Web APIs             │   │
│   │  Engine          │    │  ┌──────────────────────┐   │   │
│   │  ┌────────────┐  │    │  │  setTimeout (Timer)  │   │   │
│   │  │ Call Stack │  │    │  │  DOM APIs            │   │   │
│   │  └────────────┘  │    │  │  fetch / HTTP        │   │   │
│   └──────────────────┘    │  │  console             │   │   │
│                           │  │  GPS / Location      │   │   │
│   ┌──────────────────┐    │  └──────────────────────┘   │   │
│   │   Event Loop     │    └─────────────────────────────┘   │
│   └──────────────────┘                                      │
│   ┌──────────────────┐    ┌─────────────────────────────┐   │
│   │  Microtask Queue │    │       Task Queue            │   │
│   └──────────────────┘    └─────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

**Things provided by the browser (not the JS engine):**
- `setTimeout` / `setInterval` — Timer API
- `document.querySelector`, `getElementById` — DOM APIs
- `fetch` / HTTP requests — Network API
- `console.log` — Console API *(Yes! The console window lives in the browser's DevTools)*
- GPS / Location access
- Database access

> When you call `console.log`, it opens the **console window in DevTools** — which is part of the browser, not JavaScript itself.

## 4. The Core Components of Async JavaScript

| Component | Location | Role |
|---|---|---|
| **Call Stack** | JS Engine | Executes code; manages execution contexts |
| **Web APIs** | Browser | Provides timers, DOM, fetch, console, etc. |
| **Callback Queue (Task Queue)** | Browser | Holds callbacks from setTimeout, DOM events |
| **Microtask Queue** | Browser | Holds callbacks from Promises (higher priority) |
| **Event Loop** | Browser | Monitors call stack + queues; moves callbacks to call stack |

## 5. `setTimeout` — The Timer API

### Code Example

```javascript
console.log("Let's begin");

setTimeout(function() {
  console.log("Let's wait");
}, 4000);

console.log("Bye bye");
```

### Step-by-Step Execution

```
Step 1: GEC created → Call Stack: [GEC]

Step 2: console.log("Let's begin") executes
        Output: "Let's begin"

Step 3: setTimeout encountered
        → Browser takes over: starts a 4-second timer
        → Callback function held by the browser (NOT in call stack)
        → JS engine gets control back immediately

Step 4: console.log("Bye bye") executes
        Output: "Bye bye"

Step 5: GEC removed from Call Stack → Call Stack: []

Step 6: After 4 seconds, browser pushes callback into Task Queue
        Task Queue: [callback → console.log("Let's wait")]

Step 7: Event Loop checks:
        ✅ Call Stack is empty?  YES
        ✅ Anything in Microtask Queue?  NO
        ✅ Anything in Task Queue?  YES
        → Event Loop pushes callback onto Call Stack

Step 8: Callback executes → Output: "Let's wait"
        Callback removed from Call Stack
```

**Final Output (in order):**
```
Let's begin
Bye bye
Let's wait    ← appears after 4 seconds
```

> The callback function is called a **"callback"** because it has to be **called back** — it was handed to the browser, and when ready, it gets called back into the call stack.

## 6. The Event Loop — Heart of Async JavaScript

The **Event Loop** is a continuously running loop inside the browser (not the JS engine). Its job:

```
LOOP:
  1. Check if Call Stack is empty
  2. If empty → check Microtask Queue
     - If Microtask Queue has callbacks → push to Call Stack, execute
     - Repeat until Microtask Queue is empty
  3. If Microtask Queue is empty → check Task Queue
     - If Task Queue has a callback → push ONE callback to Call Stack
  4. Repeat forever
```

### Visualization

```
Web APIs          Callback Queues          Call Stack
──────────        ────────────────         ──────────
Timer ──────→  Task Queue       ──┐
DOM events ──→  [cb1, cb2...]     │   Event   [executing...]
                                  ├── Loop ──→
Promises ──→  Microtask Queue   ──┘
fetch    ──→  [p1, p2...]
```

## 7. DOM Events — Event Listeners

### Code Example

```javascript
console.log("Let's start");

document.getElementById("btn").addEventListener("click", function() {
  console.log("Button clicked");
});

console.log("Bye bye");
```

### Step-by-Step Execution

```
Step 1: GEC created → Call Stack: [GEC]

Step 2: console.log("Let's start") executes
        Output: "Let's start"

Step 3: addEventListener encountered
        → Browser Web API registers a "click" event on the button
        → The callback function is stored with the event in the browser
        → JS engine moves on immediately (does NOT wait for click)

Step 4: console.log("Bye bye") executes
        Output: "Bye bye"

Step 5: GEC removed from Call Stack → Call Stack: []

--- [User clicks the button at some point] ---

Step 6: Browser detects the click event
        → Pushes callback into Task Queue
        Task Queue: [callback → console.log("Button clicked")]

Step 7: Event Loop checks:
        ✅ Call Stack is empty?  YES
        ✅ Microtask Queue empty?  YES
        ✅ Task Queue has callback?  YES
        → Pushes callback onto Call Stack

Step 8: Callback executes → Output: "Button clicked"
```

**Output:**
```
Let's start
Bye bye
Button clicked    ← appears whenever the user clicks the button
```

> Notice: `"Button clicked"` always appears **after** `"Bye bye"` — even if the user clicks instantly — because it's an async event pushed through the Task Queue.

## 8. Promises and the Microtask Queue

A **Promise** represents the eventual completion (or failure) of an asynchronous operation, typically used to get data from an API or server.

- **Resolved** → request was successful; returns the value
- **Rejected** → request failed; returns the error/reason

### Code Example

```javascript
console.log("Let's start");

new Promise(function(resolve, reject) {
  resolve("done");
}).then(function(res) {
  console.log(res);
});

console.log("Bye bye");
```

### Step-by-Step Execution

```
Step 1: GEC created → Call Stack: [GEC]

Step 2: console.log("Let's start") executes
        Output: "Let's start"

Step 3: new Promise(...) encountered
        → Browser Web API creates a Promise
        → Promise is already resolved (resolve("done") called immediately)
        → The .then() callback is pushed into the MICROTASK QUEUE
        Microtask Queue: [callback → console.log(res)]

Step 4: console.log("Bye bye") executes
        Output: "Bye bye"

Step 5: GEC removed → Call Stack: []

Step 6: Event Loop checks:
        ✅ Call Stack empty?  YES
        ✅ Microtask Queue has callback?  YES (higher priority!)
        → Pushes .then() callback onto Call Stack

Step 7: Callback executes → Output: "done"
```

**Output:**
```
Let's start
Bye bye
done
```

## 9. Task Queue vs. Microtask Queue — Priority

There are **two separate callback queues**:

| Queue | Contents | Priority |
|---|---|---|
| **Microtask Queue** | Promise callbacks (`.then`, `.catch`), `queueMicrotask()` | ✅ **Higher** — executed first |
| **Task Queue** (Callback Queue) | `setTimeout`, `setInterval`, DOM event callbacks | ⚠️ **Lower** — executed after microtasks |

### Why Promises Have Higher Priority
Promises are typically used to **fetch data from an API** — you want that data shown to the user **as soon as possible**. `setTimeout` is typically used for delays, which are lower priority.

### Code Example — setTimeout vs. Promise

```javascript
console.log("Let's start");

setTimeout(function() {
  console.log("From setTimeout");      // → goes to Task Queue
}, 0);

new Promise(function(resolve, reject) {
  resolve("From Promise");
}).then(function(res) {
  console.log(res);                    // → goes to Microtask Queue
});

console.log("Bye bye");
```

### Step-by-Step Execution

```
Step 1: console.log("Let's start") → Output: "Let's start"

Step 2: setTimeout(cb, 0) encountered
        → Timer API: timer starts (0ms — expires almost instantly)
        → Once timer expires: callback pushed into Task Queue
        Task Queue: [setTimeout callback]

Step 3: new Promise(...) encountered
        → Promise resolved immediately
        → .then() callback pushed into Microtask Queue
        Microtask Queue: [promise callback]

Step 4: console.log("Bye bye") → Output: "Bye bye"

Step 5: GEC removed → Call Stack: []

Step 6: Event Loop checks queues:
        ✅ Call Stack empty?  YES
        ✅ Microtask Queue has callback?  YES → EXECUTE FIRST
        → Pushes promise callback onto Call Stack
        Output: "From Promise"
        Microtask Queue now empty

Step 7: Event Loop checks again:
        ✅ Microtask Queue empty?  YES
        ✅ Task Queue has callback?  YES
        → Pushes setTimeout callback onto Call Stack
        Output: "From setTimeout"
```

**Output:**
```
Let's start
Bye bye
From Promise       ← Microtask (higher priority)
From setTimeout    ← Task Queue (lower priority)
```

> Even though `setTimeout` had a **0ms delay** and its callback was ready before the Promise callback, the **Promise callback ran first** because the Microtask Queue has higher priority.

## 10. Multiple Promises — Microtask Queue Order

Callbacks in the Microtask Queue follow **First In, First Out (FIFO)** order.

### Code Example

```javascript
console.log("Let's start");

new Promise(function(resolve) {
  resolve("First promise resolved");
}).then(function(res) {
  console.log(res);
});

new Promise(function(resolve) {
  resolve("Second promise resolved");
}).then(function(res) {
  console.log(res);
});

console.log("Bye bye");
```

### Step-by-Step Execution

```
Step 1: console.log("Let's start") → Output: "Let's start"

Step 2: First Promise created and resolved
        → First .then() callback pushed into Microtask Queue
        Microtask Queue: [cb1]

Step 3: Second Promise created and resolved
        → Second .then() callback pushed into Microtask Queue
        Microtask Queue: [cb1, cb2]

Step 4: console.log("Bye bye") → Output: "Bye bye"

Step 5: GEC removed → Call Stack: []

Step 6: Event Loop:
        ✅ Microtask Queue has cb1 → push to Call Stack
        Output: "First promise resolved"
        Microtask Queue: [cb2]

Step 7: Event Loop:
        ✅ Microtask Queue has cb2 → push to Call Stack
        Output: "Second promise resolved"
        Microtask Queue: []
```

**Output:**
```
Let's start
Bye bye
First promise resolved
Second promise resolved
```

## 11. Complete Example — All Together

```javascript
console.log("Let's start");

function delay() {
  console.log("From delay function");

  setTimeout(function() {
    console.log("Waited for so long");   // → Task Queue
  }, 0);
}

delay();

new Promise(function(resolve) {
  resolve("Promise callback 1");
}).then(function(res) {
  console.log(res);                      // → Microtask Queue
});

new Promise(function(resolve) {
  resolve("Promise callback 2");
}).then(function(res) {
  console.log(res);                      // → Microtask Queue
});

console.log("Bye bye");
```

### Execution Flow Diagram

```
CALL STACK          MICROTASK QUEUE        TASK QUEUE
──────────          ───────────────        ──────────
[GEC]

→ "Let's start"

→ delay() called
  [delay FEC]
  → "From delay function"
  → setTimeout encountered
                                           [setTimeout cb]
  delay() done → FEC removed

→ Promise 1 resolved
                    [promise cb 1]

→ Promise 2 resolved
                    [promise cb 1, promise cb 2]

→ "Bye bye"

→ GEC removed → Call Stack EMPTY

Event Loop → Microtask Queue first:
  → promise cb 1 → "Promise callback 1"
  → promise cb 2 → "Promise callback 2"
  → Microtask Queue empty

Event Loop → Task Queue next:
  → setTimeout cb → "Waited for so long"
```

**Final Output:**
```
Let's start
From delay function
Bye bye
Promise callback 1
Promise callback 2
Waited for so long
```

## 12. Summary

```
How Async JavaScript Works
│
├── JavaScript's Nature
│   ├── Single-threaded: one thing at a time
│   └── Synchronous: line by line, in order
│
├── Async = Code divided into chunks
│   ├── Execute NOW (synchronous code)
│   └── Execute LATER (when timer/event/response is ready)
│
├── Browser Components (NOT the JS Engine)
│   ├── Web APIs: setTimeout, DOM, fetch, console, GPS
│   ├── Task Queue: setTimeout, DOM event callbacks (lower priority)
│   ├── Microtask Queue: Promise callbacks (higher priority)
│   └── Event Loop: monitors call stack + queues
│
├── Event Loop Algorithm
│   1. Is call stack empty?
│   2. If yes → drain Microtask Queue first (all tasks)
│   3. Then → execute ONE task from Task Queue
│   4. Repeat forever
│
├── Code Examples
│   ├── setTimeout → callback → Task Queue → Event Loop → Call Stack
│   ├── addEventListener → callback → Task Queue (on event fire)
│   ├── Promise.then → callback → Microtask Queue (higher priority)
│   └── Mixed (Promise + setTimeout) → Promise always runs first
│
└── Key Rule
    Microtask Queue > Task Queue
    Even a setTimeout(fn, 0) runs AFTER all pending Promise callbacks
```
