# Introduction to React

---

## What is React?

React is an **open-source JavaScript library** created by Facebook (Meta) in **2011** to solve a specific problem: efficiently updating the UI when data changes. It was originally built for Facebook's internal platform, then open-sourced for everyone to use.

> React is not magic — it is just a **JavaScript function** that solves the problem of complexity. Every React component is a function that returns HTML. That's it.

```js
// This is React — a function that returns HTML
function App() {
  return <h1>Hello World</h1>;
}
```

React was named **"React"** because it **reacts** to state changes — whenever a variable's value changes, React automatically updates every part of the UI that uses that variable, without you having to manually select DOM elements.

---

## Why React Was Created — The Problem

### The Vanilla JS Approach

Before React, developers used plain DOM manipulation to update the UI:

```html
<!-- index.html -->
<button id="btn">Increase</button>
<h1 id="count"></h1>
<p id="para"></p>
```

```js
let count = 0;

const btn = document.querySelector('#btn');
btn.addEventListener('click', () => {
  count++;
  document.querySelector('#count').textContent = count;
  document.querySelector('#para').textContent = count; // manual update
});
```

This works for small apps. But as the app grows:

- If **50 components** display the same `count`, you need to manually select and update all 50.
- Every update requires explicit `document.querySelector()` calls.
- The code becomes repetitive, complex, and hard to maintain.
- The complexity grows as **O(N⁴)** for deeply nested trees.

### What React Does Differently

React **automatically propagates state changes** to every component that uses that state — no manual DOM selection needed:

```jsx
// React — count updates everywhere automatically
import { useState } from 'react';

function App() {
  const [count, setCount] = useState(0);

  return (
    <>
      <button onClick={() => setCount(count + 1)}>Increase</button>
      <h1>{count}</h1>      {/* auto-updates */}
      <p>{count}</p>        {/* auto-updates */}
    </>
  );
}
```

One state change → React reacts → all nodes using that value update automatically. **That is the entire point of React.**

## React is a Library (Not a Framework) — But Also a Framework

React **started as a library** — it solved a single problem: efficient re-rendering. Over time, due to its extensive ecosystem, it is now widely considered a **framework**.

| | Library | Framework |
|---|---|---|
| **Definition** | Solves a singular problem | Provides end-to-end development |
| **Flexibility** | High — you control structure | Opinionated — rules must be followed |
| **Ownership** | Owns nothing — borrows everything | Bundles everything |
| **Example** | React | Next.js, Angular |

**React borrows everything via NPM:**

```bash
npm install react-router-dom   # routing
npm install react-redux        # state management
npm install tailwindcss        # styling
```

React itself is just the re-rendering engine. The surrounding ecosystem makes it a framework.

## The Real DOM vs Virtual DOM

### Real DOM (Actual DOM)

The browser renders a tree structure of HTML elements. When any element changes:

1. The change is detected
2. The **layout engine** recalculates positions
3. The **compositor** layers the page
4. The page is **repainted**

This process (called **Conciliation / CRP**) is expensive. In large apps with 50,000+ lines of code, iterating the entire tree on every change has a complexity of **O(N⁴)** in the worst case.

### Virtual DOM

React's solution: create a **lightweight JavaScript copy** of the real DOM stored in **memory (RAM)**.

```
Real DOM (browser)          Virtual DOM (in memory)
──────────────────         ──────────────────────────
<div>                       { type: 'div', props: {},
  <h1>Hello</h1>      →      children: [
  <p>World</p>                { type: 'h1', value: 'Hello' },
</div>                        { type: 'p', value: 'World' }
                             ]}
```

React never touches the real DOM directly. It works on two Virtual DOM snapshots:

- **Virtual DOM 1** — current state (what is on screen)
- **Virtual DOM 2 (Progress Tree)** — new desired state after update

These two are compared using the **Diffing Algorithm**.

---

## The Diffing Algorithm

The **Diffing Algorithm** compares Virtual DOM 1 with Virtual DOM 2 and finds the minimum set of changes needed. It uses the analogy: **Virtual DOM 2 minus Virtual DOM 1 = what changed**.

### Three Types of Changes

| Scenario | What React Does |
|---|---|
| Only the **content** changed (same tag) | Updates only the text content — fastest |
| The **tag** changed (e.g., `<h1>` → `<p>`) | Creates new element, replaces old one |
| **Tag + content** both changed | Decides smartest approach — create new node or update both |

React decides the **smarter approach** automatically. This is called **amputation and replacement** — remove the old node, inject the new one.

### Example: Amputation and Replacement

```
Virtual DOM 1              Virtual DOM 2 (Progress Tree)
─────────────              ─────────────────────────────
<h1 id="x">              → <p id="key">
  because                    Aryan
</h1>                      </p>
```

React detects: tag changed from `h1` to `p`, content changed. It creates a new `<p>` node with the new value and replaces the old `<h1>`.

---

## Reconciliation

**Reconciliation** is the full process React uses to detect changes and update the real DOM:

1. State or props change in a component
2. React creates a **new Virtual DOM tree** (Progress Tree)
3. The **Diffing Algorithm** compares new vs old Virtual DOM
4. React determines the minimal set of changes
5. Only changed nodes are updated in the **real DOM**

> **Conciliation** = one pass of detecting and reflecting a change.
> **Reconciliation** = this process happening repeatedly as state updates occur.

Reconciliation is NOT separate from the Virtual DOM — they are the same concept. Reconciliation is the **implementation** name. Virtual DOM is the **concept** name.

## React Fiber Architecture

### The Problem with Old Reconciliation (Stack Reconciler)

The old reconciliation algorithm worked **synchronously** — like a stack, top to bottom, node by node. It could not be interrupted.

**Problem:** If React is rendering 1,000 list items synchronously, the UI freezes. The user cannot type, scroll, or interact until rendering finishes.

```
Render 1000 items → UI frozen → User clicks button → Nothing responds
```

### React Fiber (Introduced in React 16)

React **rewrote the entire reconciliation algorithm** in 2016. The new algorithm is called **Fiber**.

> React Fiber is an ongoing re-implementation of React's core algorithm. The goal of React Fiber is to increase its suitability for animations, layout, and gestures.

**What Fiber can do that the old algorithm could not:**

| Feature | Old Reconciler | React Fiber |
|---|---|---|
| Pause work | No | Yes |
| Resume work | No | Yes |
| Reuse completed work | No | Yes |
| Abort unnecessary work | No | Yes |
| Assign priority to updates | No | Yes |
| Concurrent rendering | No | Yes (React 18+) |

### The Lunch Box Analogy (from the lecture)

**Old approach (fast but inefficient):**
- Go to kitchen, grab curry (only thing ready), run back.
- Go again, grab 2 chapatis, run back.
- Go again, grab more chapatis, run back.
- 6–7 trips. Fast individually, but wasteful overall.

**Fiber approach (smart and efficient):**
- Go to kitchen, **wait 10 minutes** for everything to be ready.
- Pack everything into one box.
- Make **one single trip** back.
- **Same total time, but one delivery — no partial, flickering updates.**

Fiber can also **prioritise** — animations (high priority) are rendered before background data updates (low priority).

### Incremental Rendering

React Fiber uses **incremental rendering**: breaking rendering work into small chunks (frames) and spreading them across multiple browser frames. This keeps the UI smooth even during heavy computation.

```
Instead of:  [ Render all 1000 items at once → UI freezes ]
Fiber does:  [ Chunk 1 ] → [ Chunk 2 ] → [ Chunk 3 ] → smooth UI
```

### 70/30 Formula

Modern React uses a combination of:

- **70% Fiber** — batch updates, prioritised rendering
- **30% HMR (Hot Module Replacement)** — near-instant delivery of changes (< 100ms)

> Being fast (HMR) + being efficient (Fiber) = smooth, responsive applications.

### Fiber & React 18 — Lanes

React 18 introduces **"lanes"** — a priority system where:

- **Urgent work** (typing, clicks) can interrupt low-priority work
- **Background updates** (data fetching, transitions) run when the thread is free
- `startTransition()` marks updates as non-urgent

## JSX — JavaScript + XML

In React, components are written in **JSX (JavaScript XML)** — a syntax that looks like HTML but is actually JavaScript.

```jsx
// This looks like HTML but is JSX
function Welcome() {
  return <h1>Welcome to React Class</h1>;
}
```

**JSX is not understood by the browser.** It gets transformed by a **Babel transpiler** into plain JavaScript:

```js
// What Babel converts JSX into behind the scenes
React.createElement('h1', null, 'Welcome to React Class');
```

The browser only understands HTML, CSS, and JS — Babel converts JSX to JS so the browser can run it.

### Key files explained

**`index.html`** — The single HTML page. Contains only an empty `<div id="root">`:

```html
<body>
  <div id="root"></div>
  <script type="module" src="/src/main.jsx"></script>
</body>
```

**`main.jsx`** — Entry point. Mounts the React app into `#root` using DOM manipulation:

```jsx
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

This code does three things:

1. **Creates a React root** attached to the DOM element with `id="root"` — this is where `createRoot()` creates the Virtual DOM.
2. **Renders the `App` component** into that root.
3. **Enables StrictMode** for everything inside `App`.

> `createRoot()` = creating a Virtual DOM. React then manages all updates from there.

### `StrictMode` — In Depth

`StrictMode` is a special React component that helps you find potential problems in your application during **development**. It does **not render anything to the UI** and has **zero effect in production builds**.

Think of it as React's **"extra inspection mode"** — it stress-tests your components to make sure they behave correctly before reaching users.

#### What StrictMode Actually Does

**1. Detects unsafe side effects**

React expects components to be **pure functions** — given the same props, they should always return the same output without modifying anything outside:

```jsx
// ✅ Pure — safe
function Greeting({ name }) {
  return <h1>Hello {name}</h1>;
}

// ❌ Impure — modifies external state during render
let counter = 0;

function App() {
  counter++; // side effect during render!
  console.log(counter);
  return <h1>Hello</h1>;
}
```

StrictMode helps expose these kinds of problems before they cause bugs.

**2. Intentionally renders components twice in development**

This is the behaviour that surprises most beginners. With StrictMode:

```jsx
function App() {
  console.log("Rendering App");
  return <h1>Hello</h1>;
}
```

Console output:

```
Rendering App
Rendering App
```

React intentionally calls your component **twice** during development to verify that rendering does not produce side effects. The double render makes unintended side effects (like API calls inside the render body) immediately obvious:

```jsx
// ❌ BAD — side effect during render
function App() {
  fetch('/api/users'); // will fire twice in StrictMode!
  return <h1>Hello</h1>;
}
```

**3. Re-runs Effects to detect cleanup issues**

```jsx
useEffect(() => {
  console.log("Connected");

  return () => {
    console.log("Disconnected");
  };
}, []);
```

Under StrictMode, you will see:

```
Connected
Disconnected
Connected
```

React mounts → unmounts → remounts to test whether your effect sets up correctly AND your cleanup function properly releases resources. This helps find **memory leaks**.

**With cleanup (correct):**

```jsx
useEffect(() => {
  const id = setInterval(() => {
    console.log("Running");
  }, 1000);

  return () => clearInterval(id); // ✅ cleans up properly
}, []);
```

**Without cleanup (memory leak):**

```jsx
useEffect(() => {
  setInterval(() => {
    console.log("Running");
  }, 1000);
  // ❌ no cleanup — interval keeps running after unmount
}, []);
```

StrictMode's mount/unmount/remount cycle makes this problem immediately visible.

**4. Warns about deprecated React APIs**

StrictMode identifies usage of older APIs that React plans to remove, helping you keep your codebase up to date.

#### Why is my API call firing twice?

A very common question from beginners:

```jsx
useEffect(() => {
  fetch('/api/users');
}, []);
```

In development with StrictMode:

```
GET /api/users
GET /api/users   ← StrictMode remount
```

In production build (`npm run build`):

```
GET /api/users   ← fires only once
```

StrictMode causes this — it is expected behaviour in development, not a bug.

#### Should you remove StrictMode?

You can:

```jsx
// Without StrictMode
createRoot(document.getElementById('root')).render(<App />);
```

But it is **strongly recommended to keep it**. It only runs in development and helps catch bugs before they reach users.

#### StrictMode Summary

| Behaviour | Development | Production |
|---|---|---|
| Renders components twice | Yes | No |
| Remounts effects (setup + cleanup + setup) | Yes | No |
| Warns about deprecated APIs | Yes | No |
| Affects UI or visible output | No | No |
| Affects performance for users | No | No |

## Components

A **component** is the main building block of a React application. It is a JavaScript function that:

- Starts with a **capital letter** (required)
- Returns **JSX** (HTML-like syntax)
- Can be reused anywhere in the app

```jsx
// Home.jsx — a component
function Home() {
  return <h2>This is the Home page</h2>;
}

export default Home;
```

### Rules of Components

1. **Capital first letter** — `Home`, not `home`
2. **Return one parent element** — wrap multiple elements in a `<div>` or React Fragment `<>`
3. **File extension** — `.jsx` or `.js` (`.tsx` for TypeScript)

### React Fragment — avoid extra `<div>` wrappers

```jsx
// Bad — adds an unnecessary div to the DOM
return (
  <div>
    <Navbar />
    <Home />
    <About />
  </div>
);

// Good — Fragment leaves no trace in the DOM
return (
  <>
    <Navbar />
    <Home />
    <About />
  </>
);
```

### Using Components in App.jsx

```jsx
import Navbar from './components/Navbar';
import Home from './components/Home';
import About from './components/About';

function App() {
  return (
    <>
      <Navbar />
      <Home />
      <About />
    </>
  );
}

export default App;
```

## Events in React — Event Handling vs Event Listening

In React, **you cannot use `addEventListener()`** directly on elements because React works on the **Virtual DOM**, not the real DOM. Virtual DOM nodes are not physically in the browser, so you cannot "listen" to them.

### ❌ Event Listening (Does NOT work in React)

```jsx
// This will fail — null reference to a virtual node
const btn = document.querySelector('#btn');
btn.addEventListener('click', () => {
  alert('clicked');
});
```

**Why it fails:** The element doesn't exist in the real DOM during React's render cycle. `document.querySelector` returns `null`.

### ✅ Event Handling (Correct React approach)

Pass the handler directly on the JSX element using `on + EventName`:

```jsx
function App() {
  const handleClick = () => {
    alert('Button was clicked!');
  };

  return <button onClick={handleClick}>Click Me</button>;
}
```

### Common React Event Handlers

| Event Type | Handler |
|---|---|
| Click | `onClick` |
| Double click | `onDoubleClick` |
| Mouse enter | `onMouseEnter` |
| Mouse leave | `onMouseLeave` |
| Key down | `onKeyDown` |
| Key up | `onKeyUp` |
| Form submit | `onSubmit` |
| Input change | `onChange` |
| Focus | `onFocus` |
| Blur | `onBlur` |
| Touch start | `onTouchStart` |
| Touch end | `onTouchEnd` |

## React Synthetic Events

### What Are Synthetic Events?

When a user interacts with the browser, a **native DOM event** is fired. React intercepts this event and wraps it in a **Synthetic Event** — a cross-browser compatible wrapper.

Think of it like this: React has a **butler** who:

1. Listens to all browser events at the **root level** (not individual elements)
2. Wraps them into a consistent format (Synthetic Event)
3. Delivers them to your event handler

```js
function Button() {
  const handleClick = (event) => {
    console.log(event.type);   // "click" — works in all browsers
    console.log(event.target); // the button element
  };

  return <button onClick={handleClick}>Click Me</button>;
}
```

### How React Handles Events — The Flow

```
[User Clicks] 
      ↓
[Native DOM Event fires and bubbles up]
      ↓
[React intercepts at the ROOT level]
      ↓
[Wraps in a Synthetic Event ✉️]
      ↓
[Delivers to your component's handler]
```

React uses **event delegation** — instead of attaching listeners to every individual element, it attaches **one single listener at the root**. This is much more memory-efficient.

### Synthetic Event vs Native Event

| Feature | Native DOM Event | React Synthetic Event |
|---|---|---|
| Cross-browser compatible | No (inconsistencies exist) | Yes |
| Attached to | Individual elements | Root level (event delegation) |
| Memory usage | Higher | Lower |
| API consistency | Varies by browser | Unified API |

### Event Pooling (React 16 and earlier)

In older versions of React, Synthetic Events were **pooled** (recycled) for memory efficiency. The event object was nullified after the handler ran:

```js
// ❌ Event might be null after handler finishes (React 16)
function handleClick(event) {
  setTimeout(() => {
    console.log(event.type); // null — event was recycled!
  }, 1000);
}

// ✅ Use event.persist() to keep the event alive
function handleClick(event) {
  event.persist();
  setTimeout(() => {
    console.log(event.type); // "click" — safe!
  }, 1000);
}
```

> In **React 17+**, event pooling was removed. `event.persist()` is no longer needed but still works without effect.

### Stopping Event Propagation

Events in React still bubble through the React component tree. Use `event.stopPropagation()` to stop bubbling:

```jsx
function Modal({ onClose, children }) {
  return ReactDOM.createPortal(
    <div className="overlay" onClick={onClose}>
      {/* Clicking the modal itself won't close it */}
      <div className="modal" onClick={(e) => e.stopPropagation()}>
        {children}
        <button onClick={onClose}>Close</button>
      </div>
    </div>,
    document.getElementById('modal-root')
  );
}
```

## React Portals

### What is a React Portal?

A **React Portal** allows you to render a component **outside its parent DOM hierarchy** while keeping it part of the React component tree.

Think of it like Doctor Strange's portals — you remain in one place (React tree) but your component appears somewhere else (different DOM node).

### When to Use Portals

- **Modals** — need to escape `overflow: hidden` or `z-index` restrictions from parent containers
- **Tooltips** — need to appear above all other elements
- **Dropdown menus** — need to overflow their container
- **Context menus** — need to be positioned freely on screen

### Setup — Add Portal Target in HTML

```html
<body>
  <div id="root"></div>
  <div id="modal-root"></div>  <!-- Portal target -->
</body>
```

### Basic Portal Syntax

```jsx
import ReactDOM from 'react-dom';

function Modal({ children }) {
  return ReactDOM.createPortal(
    <div className="modal">{children}</div>,
    document.getElementById('modal-root') // renders here, not inside #root
  );
}
```

### Full Modal Example

```jsx
import { useState } from 'react';
import ReactDOM from 'react-dom';

function Modal({ onClose, children }) {
  return ReactDOM.createPortal(
    <div className="overlay" onClick={onClose}>
      <div className="modal" onClick={(e) => e.stopPropagation()}>
        {children}
        <button onClick={onClose}>Close</button>
      </div>
    </div>,
    document.getElementById('modal-root')
  );
}

function App() {
  const [isOpen, setIsOpen] = useState(false);

  return (
    <div>
      <button onClick={() => setIsOpen(true)}>Open Modal</button>
      {isOpen && (
        <Modal onClose={() => setIsOpen(false)}>
          <p>This modal lives in #modal-root, not #root!</p>
        </Modal>
      )}
    </div>
  );
}
```

### Reusable Portal Component

```jsx
function Portal({ children, targetId }) {
  const target = document.getElementById(targetId);
  return target ? ReactDOM.createPortal(children, target) : null;
}

// Usage
<Portal targetId="modal-root">
  <p>Renders outside the parent tree.</p>
</Portal>
```

### Portal vs Normal Rendering

| Feature | Normal Rendering | Portal |
|---|---|---|
| Renders inside parent DOM | Yes | No (renders in target) |
| Part of React component tree | Yes | Yes |
| Inherits React context | Yes | Yes |
| Event bubbling | Through DOM parent | Through React tree |
| Affected by parent CSS | Yes | No |

> Even though a portal renders outside the parent DOM, **events still bubble through the React component tree** — not the DOM tree. This is a key distinction.

## Single Page Application (SPA)

React apps are **Single Page Applications (SPAs)**. No matter how many pages your app has, only **one HTML file** (`index.html`) is sent to the browser.

All "pages" are JavaScript components that are:

1. Written in separate `.jsx` files
2. **Bundled** into a single file by the build tool (Vite/Webpack)
3. **Injected** into `index.html` via DOM manipulation at runtime

```
Multiple .jsx files  →  Bundler (Vite)  →  index.html + bundle.js
     (source)                                   (production)
```

This is how your browser only ever sees one HTML page but the app feels like it has multiple pages — React Router swaps components in and out without a full page reload.

## Pages vs Layout vs Component vs Screen

A common interview question: **what is the difference between these four terms?**

| Term | Description | Example |
|---|---|---|
| **Component** | Smallest reusable building block. Returns JSX. | `<Button />`, `<Card />`, `<Input />` |
| **Layout** | Wraps multiple components in a structural template | `<Header />` + `<Sidebar />` + `<Footer />` |
| **Page** | A full route — a composition of layouts + components | `HomePage`, `AboutPage`, `LoginPage` |
| **Screen** | Used in mobile (React Native) — equivalent to a page | `HomeScreen`, `ProfileScreen` |

```
Screen / Page
└── Layout
    ├── Navbar (Component)
    ├── Sidebar (Component)
    └── Content Area
        ├── Card (Component)
        └── Button (Component)
```

## List and Keys

When rendering arrays in React, each element must have a unique **`key`** prop. Without keys, React cannot track which items changed, were added, or removed.

```jsx
// ❌ Without keys — React may remount wrong items
const items = ['Apple', 'Banana', 'Cherry'];
return items.map(item => <li>{item}</li>);

// ✅ With stable unique keys
return items.map((item, id) => <li key={id}>{item}</li>);

// ✅ Best — use actual unique IDs from data
return products.map(product => <li key={product.id}>{product.name}</li>);
```

**Why not use array index as a key?**

If you insert an item at the beginning, all indexes shift. React maps components to the wrong data, causing state bugs and visual glitches.

## Summary

| Concept | Key Takeaway |
|---|---|
| **React** | A JS function that automatically updates UI when state changes |
| **Why React** | Eliminates manual DOM selection for shared state across components |
| **Virtual DOM** | An in-memory copy of the real DOM stored as a JS object tree |
| **Diffing Algorithm** | Compares two Virtual DOMs to find minimum changes needed |
| **Reconciliation** | The full process: detect → diff → update real DOM |
| **React Fiber** | Rewrite of reconciliation — async, pauseable, prioritised |
| **Incremental Rendering** | Work split into chunks, spread over frames — smooth UI |
| **JSX** | JS + HTML syntax, transpiled to plain JS by Babel |
| **Component** | A JS function returning JSX — starts with capital letter |
| **SPA** | One HTML file — all "pages" are JS components bundled together |
| **Synthetic Events** | Cross-browser event wrappers — use `onClick`, `onChange`, etc. |
| **Event Handling** | Use `onClick={handler}` not `addEventListener()` in React |
| **React Portal** | Render outside parent DOM while staying in React tree |
| **StrictMode** | Dev tool — renders twice to expose bugs early |
| **List & Keys** | Always give unique `key` props to list items for correct diffing |

## React Pages, Layouts & UI Components

React applications organise their structure into three distinct layers — **Pages**, **Layouts**, and **Components** — creating a clean, scalable, and maintainable architecture. Understanding this separation is essential for building production-grade React applications.

```
App
├── Layout (global shell — navbar, sidebar, footer)
│   └── Page (route-level view)
│       ├── Component (reusable UI block)
│       ├── Component
│       └── Component
```

---

### Pages

**Pages** correspond to **routes** and provide the top-level views of the application. Each page:

- Maps to a specific URL route (e.g. `/products`, `/users`, `/dashboard`)
- Wraps its content inside a **Layout component** (e.g. `PageLayout`)
- Groups related elements and features together

```
src/
└── pages/
    ├── products/
    │   ├── ProductsList.jsx       # main view / entry point for this route
    │   ├── ProductModal.jsx       # modal component (specific to products)
    │   ├── EditButton.jsx         # edit action component
    │   └── column-config.js       # data table column configuration
    ├── users/
    │   ├── UsersList.jsx
    │   ├── UserModal.jsx
    │   └── column-config.js
    └── tenants/
        ├── TenantsList.jsx
        └── column-config.js
```

**How Pages Work:**

Each page wraps its content in a `PageLayout` component. For non-authenticated views (login, register, forgot password), a `GuestLayout` is used instead.

```jsx
// pages/products/ProductsList.jsx
import PageLayout from '../../layout/PageLayout';
import DataTable from '../../components/DataTable';
import columnConfig from './column-config';

function ProductsList() {
  return (
    <PageLayout title="Products">
      <DataTable columns={columnConfig} />
    </PageLayout>
  );
}

export default ProductsList;
```

**Guest Layout (non-authenticated pages):**

```jsx
// pages/auth/Login.jsx
import GuestLayout from '../../layout/GuestLayout';

function Login() {
  return (
    <GuestLayout>
      <h2>Login</h2>
      {/* login form */}
    </GuestLayout>
  );
}

export default Login;
```

**Organising by Feature:**

Pages group their sub-components by feature, not by type. Everything related to the `products` feature lives in `pages/products/` — the list view, modal, edit button, and column configuration all together. This is called **feature-based folder structure** and scales much better than grouping by component type.

```
❌ Type-based (harder to scale)       ✅ Feature-based (recommended)
───────────────────────────────       ──────────────────────────────
components/                           pages/
  modals/ProductModal.jsx               products/
  buttons/EditButton.jsx                  ProductsList.jsx
  tables/ProductsTable.jsx                ProductModal.jsx
pages/                                    EditButton.jsx
  ProductsList.jsx                        column-config.js
```

**Client-side vs Server-side Data Tables:**

Different pages may use different data strategies:

| Page | Data Table Type | When to Use |
|---|---|---|
| `pages/users` | Client-side | Small datasets — all data loaded upfront, filtering done in browser |
| `pages/tenants` | Client-side | Same as above |
| `pages/products` | Server-side | Large datasets — data fetched per page/filter from the API |

### Layout

**Layouts** are the **global shell** components that wrap pages. They provide consistent structure — navigation, sidebars, headers, footers — across multiple views.

```
src/
└── layout/
    ├── PageLayout.jsx       # authenticated app shell
    ├── GuestLayout.jsx      # unauthenticated shell (login/register)
    ├── SidebarNav.jsx       # left navigation sidebar
    ├── TopBar.jsx           # top header bar
    └── menu-options.js      # navigation menu items (array of objects)
```

```jsx
// layout/PageLayout.jsx
import SidebarNav from './SidebarNav';
```

### Components

**Components** are **reusable UI elements** that are not specific to any one page. They live in the `/components` folder and can be used across multiple pages and features.

```
src/
└── components/
    ├── DataTable.jsx          # reusable data table
    ├── LoadingButton.jsx      # button with loading state
    ├── Breadcrumb.jsx         # navigation breadcrumb trail
    ├── Modal.jsx              # generic modal wrapper
    ├── Badge.jsx              # status badge
    └── SearchInput.jsx        # search field
```

**Rule:** If a component is used in **more than one place**, it belongs in `/components`. If it is only used by one feature, it belongs inside that feature's page folder.

**Example — Reusable LoadingButton:**

```jsx
// components/LoadingButton.jsx
function LoadingButton({ isLoading, onClick, children }) {
  return (
    <button onClick={onClick} disabled={isLoading}>
      {isLoading ? 'Loading...' : children}
    </button>
  );
}

export default LoadingButton;
```

**Used across multiple pages:**

```jsx
// pages/products/ProductsList.jsx
import LoadingButton from '../../components/LoadingButton';

<LoadingButton isLoading={isSaving} onClick={handleSave}>
  Save Product
</LoadingButton>
```

```jsx
// pages/users/UsersList.jsx
import LoadingButton from '../../components/LoadingButton';

<LoadingButton isLoading={isDeleting} onClick={handleDelete}>
  Delete User
</LoadingButton>
```

**Example — Breadcrumb Component:**

```jsx
// components/Breadcrumb.jsx
function Breadcrumb({ items }) {
  return (
    <nav className="breadcrumb">
      {items.map((item, index) => (
        <span key={index}>
          {index < items.length - 1 ? (
            <a href={item.path}>{item.label}</a>
          ) : (
            <span>{item.label}</span>
          )}
          {index < items.length - 1 && ' / '}
        </span>
      ))}
    </nav>
  );
}

// Usage
<Breadcrumb items={[
  { label: 'Home', path: '/' },
  { label: 'Products', path: '/products' },
  { label: 'Edit Product' }
]} />
```

### Data Tables & Column Config

Data tables are **reusable components** that adapt to any dataset through a **column configuration** array. Instead of hardcoding what columns to show, each page passes its own `column-config.js` to the same generic `DataTable` component.

**Column Config — array of objects:**

Each object in the array represents one column. Properties define how the column behaves and displays data:

```js
// pages/products/column-config.js
const columnConfig = [
  {
    accessorKey: 'id',
    header: 'ID',
    enableSorting: true,
    size: 60,
  },
  {
    accessorKey: 'name',
    header: 'Product Name',
    enableSorting: true,
    cell: (info) => <strong>{info.getValue()}</strong>,
  },
  {
    accessorKey: 'price',
    header: 'Price',
    enableSorting: true,
    cell: (info) => `$${info.getValue().toFixed(2)}`,
  },
  {
    accessorKey: 'status',
    header: 'Status',
    cell: (info) => (
      <Badge status={info.getValue()} />
    ),
  },
  {
    id: 'actions',
    header: 'Actions',
    cell: ({ row }) => (
      <EditButton productId={row.original.id} />
    ),
  },
];

export default columnConfig;
```

**Reusable DataTable Component:**

```jsx
// components/DataTable.jsx
import {
  useReactTable,
  getCoreRowModel,
  getSortedRowModel,
  flexRender,
} from '@tanstack/react-table';

function DataTable({ columns, data }) {
  const table = useReactTable({
    data,
    columns,
    getCoreRowModel: getCoreRowModel(),
    getSortedRowModel: getSortedRowModel(),
  });

  return (
    <table>
      <thead>
        {table.getHeaderGroups().map((headerGroup) => (
          <tr key={headerGroup.id}>
            {headerGroup.headers.map((header) => (
              <th key={header.id}>
                {flexRender(header.column.columnDef.header, header.getContext())}
              </th>
            ))}
          </tr>
        ))}
      </thead>
      <tbody>
        {table.getRowModel().rows.map((row) => (
          <tr key={row.id}>
            {row.getVisibleCells().map((cell) => (
              <td key={cell.id}>
                {flexRender(cell.column.columnDef.cell, cell.getContext())}
              </td>
            ))}
          </tr>
        ))}
      </tbody>
    </table>
  );
}

export default DataTable;
```

> The table components use **TanStack Table V8** (`@tanstack/react-table`) — a headless, framework-agnostic table library that handles sorting, filtering, pagination, and more.

### Architecture Summary

| Layer | Folder | Purpose | Examples |
|---|---|---|---|
| **Pages** | `src/pages/` | Route views, feature grouping | `ProductsList`, `UsersList`, `Login` |
| **Layout** | `src/layout/` | Global navigation & page shell | `PageLayout`, `SidebarNav`, `TopBar` |
| **Components** | `src/components/` | Reusable elements across pages | `DataTable`, `Breadcrumb`, `LoadingButton` |
| **Template Resources** | `src/template-resources/` | Sample/reference UI components | Base UI, Extended UI |

**The golden rule:**

> 1. If it is **route-specific** → it belongs in `pages/`.
> 2. If it is **used globally** → it belongs in `layout/`.
> 3. If it is **reused across multiple pages** → it belongs in `components/`.
> 4. If it is a **sample or reference** → it belongs in `template-resources/`.
