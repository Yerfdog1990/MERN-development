# Node.js & Node Package Manager

---

## What is Node.js?

**Node.js** is an open-source, cross-platform **JavaScript runtime environment** that allows JavaScript to run outside the browser — directly on a server or machine.

Before Node.js existed, JavaScript could only run inside a browser. Ryan Dahl changed this in **2009** by wrapping the **V8 JavaScript engine** (the same engine that powers Google Chrome) with a C++ library called **libuv**, creating an environment where JavaScript could interact with the operating system, file system, network, and more.

> In short: Node.js = V8 engine + libuv (C++ library for OS-level access)

---

## Why Node.js Was Created

JavaScript is **synchronous** and **single-threaded** by default — it can only do one thing at a time. If a task takes time (like reading a file or calling an API), it blocks everything else.

**The problem:** The browser's `console` can run JS just fine, but try running `console.log("hi")` in the Windows Command Prompt — it fails. JavaScript had no environment outside the browser.

**Ryan Dahl's solution:** Build a runtime that lets JavaScript run on the server side, handle file operations, and perform non-blocking I/O — without needing a separate backend language like Java, PHP, or Python.

```bash
# In the browser console — works fine
console.log("hi") # hi

# In Windows CMD — fails
console.log("hi") # 'console.log' is not recognized
```

After installing Node.js:

```bash
node index.js   # runs JavaScript outside the browser
```

---

## The V8 Engine

**V8** is the JavaScript engine built by Google that powers Chrome. It:

- Parses and executes JavaScript code
- Uses **JIT (Just-In-Time) compilation** — not purely interpreted — for faster performance
- Is written in C++ and is completely independent of the browser

Node.js took the V8 engine out of the browser and added a layer (libuv) that connects JavaScript to the operating system. This is what makes system-level operations possible.

### Other JS Engines (by browser)

| Browser | JavaScript Engine |
|---|---|
| Google Chrome | **V8** (also used by Node.js) |
| Firefox | SpiderMonkey |
| Safari | JavaScriptCore (Nitro) |
| Edge (old) | Chakra |
| Edge (new) | V8 (rebuilt on Chromium) |

All engines implement the **ECMA ES-262 standard** (ECMAScript).

## How Node.js Works — Key Concepts

### Single-Threaded, Non-Blocking I/O

Node.js runs in a **single process** and does not create a new thread for every request. Instead of blocking while waiting for slow operations (file reads, database queries, network calls), it:

1. Offloads those operations to the system kernel or a worker thread
2. Continues executing other code
3. Comes back to handle the result when it's ready via a **callback**

This is called **non-blocking I/O** and it allows Node.js to handle **thousands of concurrent connections** from a single server.

### Blocking vs Non-Blocking

**Blocking (synchronous)** — waits for the operation to finish before moving on:

```js
const fs = require('node:fs');
const data = fs.readFileSync('/file.md'); // blocks here until file is read
console.log(data);
moreWork(); // runs AFTER console.log
```

**Non-blocking (asynchronous)** — continues executing while the operation runs in the background:

```js
const fs = require('node:fs');
fs.readFile('/file.md', (err, data) => {
  if (err) throw err;
  console.log(data); // runs AFTER moreWork()
});
moreWork(); // runs FIRST — does not wait for file read
```

> The ability to run `moreWork()` without waiting for the file read to complete is a key design choice that allows for higher throughput.

### DIRTY Tasks (Data Intensive Real-Time Applications)

In the lecture, **DIRTY** was introduced as a term:

> **D**ata **I**ntensive **R**eal-**T**ime application tasks

These are heavy-duty, blocking-nature tasks. Node.js was specifically designed to handle DIRTY tasks efficiently by offloading them to worker threads so the main thread stays unblocked.

## The Event Loop

The Event Loop is the core of Node.js's non-blocking architecture. It works on the **REPL** principle:

> **R**ead → **E**valuate → **P**rint → **L**oop

Everything in Node.js is event-driven. The Event Loop continuously runs and manages two types of operations:

| Type | Description | Where handled |
|---|---|---|
| **Non-blocking** | Fast, no CPU wait (e.g., `console.log`) | Executed immediately on main thread |
| **Blocking** | Slow, CPU/I/O intensive (e.g., file read, DB query) | Offloaded to worker threads (libuv) |

### Event Loop Phases (simplified)

```
┌───────────────────────────┐
│           timers          │  → setTimeout(), setInterval()
└─────────────┬─────────────┘
              ↓
┌───────────────────────────┐
│     pending callbacks     │  → I/O callbacks deferred from previous loop
└─────────────┬─────────────┘
              ↓
┌───────────────────────────┐
│           poll            │  → retrieve new I/O events, execute callbacks
└─────────────┬─────────────┘
              ↓
┌───────────────────────────┐
│           check           │  → setImmediate() callbacks
└─────────────┬─────────────┘
              ↓
┌───────────────────────────┐
│      close callbacks      │  → socket.on('close', ...)
└───────────────────────────┘
```

### Worker Threads & Concurrency

Node.js uses **worker threads** (via libuv) to handle blocking operations. The number of available threads depends on the CPU:

```js
import os from 'os';
console.log(os.cpus().length); // e.g., 16 threads on an octa-core CPU
```

General formula:
- Dual-core → 4 threads
- Quad-core → 8 threads
- Octa-core → 16 threads

> If 20 blocking tasks arrive and only 16 threads are available, the remaining 4 must wait — this is the **bottleneck of Node.js**.

This is why production systems use **Backend as a Service (BaaS)** from cloud platforms like AWS, GCP, or Azure — they provide thousands of virtual CPUs to handle massive concurrent loads.

## The REPL Environment

Node.js comes with a built-in **REPL (Read-Eval-Print Loop)** that lets you run JavaScript interactively in the terminal.

```bash
node          # starts the REPL session
> 2 + 2       # 4
> console.log("hi")  # hi
```

### Useful REPL commands

| Command | Description |
|---|---|
| `.help` | Shows all available dot commands |
| `.editor` | Enter multi-line editor mode |
| `.break` | Abort current multi-line input |
| `.clear` | Reset REPL context |
| `.save <file>` | Save session to a file |
| `.exit` | Exit the REPL |

## A Simple Node.js HTTP Server

```js
const { createServer } = require('node:http');

const hostname = '127.0.0.1';
const port = 3000;

const server = createServer((req, res) => {
  res.statusCode = 200;
  res.setHeader('Content-Type', 'text/plain');
  res.end('Hello World\n');
});

server.listen(port, hostname, () => {
  console.log(`Server running at http://${hostname}:${port}/`);
});
```

Run it:

```bash
node server.js
# Server running at http://127.0.0.1:3000/
```

## What is NPM?

**NPM** stands for **Node Package Manager**. It is:

- The **standard package manager** for Node.js
- A **registry** (website: [npmjs.com](https://npmjs.com)) hosting over **2.1 million packages**
- A **CLI tool** to install, update, and manage dependencies

> Think of NPM like a cloud kitchen marketplace. Developers "cook" functions, package them, and host them on NPM. Anyone can install and use them with a single command.

Alternatives to npm include **Yarn** (`yarnpkg.com`) and **pnpm** (`pnpm.io`).

---

## What is a Package?

A **package** is a piece of code — one or more functions — that someone has written, bundled, and published to NPM so others can use it.

```js
// Example: figlet package converts text to ASCII art
import figlet from 'figlet';

figlet('Hello World', (err, data) => {
  if (err) return console.error(err);
  console.log(data);
});
```

React itself is just a package:

```bash
npm install react
```

When you install a package, its code is downloaded into the `node_modules/` folder of your project.

## Types of Packages / Modules

| Type | Description | Example |
|---|---|---|
| **Built-in** | Come with Node.js, no install needed | `fs`, `path`, `http`, `os`, `url` |
| **Third-party** | Published on NPM, must be installed | `express`, `react`, `figlet` |
| **Custom** | Written by you for your own project | Your own `math.js`, `utils.js` |

### Built-in modules — no install required

```js
import fs from 'fs';        // file system
import path from 'path';    // file paths
import os from 'os';        // operating system info
import http from 'http';    // HTTP server/client
```

Built-in modules have **no version number** in `package.json` — they exist from the moment Node.js is installed ("born with Node.js").

## Package Versioning (Semantic Versioning / SemVer)

Every package follows the format: `MAJOR.MINOR.PATCH`

```
1 . 2 . 3
│   │   └── PATCH — bug fixes
│   └──── MINOR — new features, backward compatible
└──────── MAJOR — breaking changes, legacy rewrite
```

**Example: `node.js` version `24.0.1`**

- `24` — 24th time the core was rewritten (major)
- `0` — zero minor updates
- `1` — one bug fix

**A newborn package = `1.0.0`** — first write, no changes yet.

### Version Range Symbols

| Symbol | Name | What it allows |
|---|---|---|
| `*` | Asterisk (global) | Any version — including major breaking changes |
| `^` | Caret | Minor + patch updates only (no major) |
| `~` | Tilde | Patch updates only (consent-based major/minor) |

```json
"dependencies": {
  "express": "^4.18.2"   // allows 4.x.x, NOT 5.x.x
}
```

> **Always use `^` (caret) in production.** It allows bug fixes and minor improvements without risking breaking changes from a major version upgrade.

**Why not `*`?** If a package you depend on rewrites its API (version 1 → version 2), the `*` selector automatically upgrades you and could break your entire application overnight.

## CommonJS vs ES Modules

Node.js supports two module systems. The approach you use is set in `package.json`.

### CommonJS (`require` / `module.exports`)

The **older, default** approach. Most legacy packages on NPM use this.

```js
// math.js — exporting
function sum(a, b) {
  return a + b;
}
module.exports = sum;

// use.js — importing
const sum = require('./math.js');
console.log(sum(4, 5)); // 9
```

Exporting multiple functions as an object:

```js
// math.js
function sum(a, b) { return a + b; }
function subtract(a, b) { return a - b; }
module.exports = { sum, subtract };

// use.js
const math = require('./math.js');
console.log(math.sum(4, 5));       // 9
console.log(math.subtract(9, 3));  // 6
```

### ES Modules (`import` / `export`)

The **modern** approach. Enable by adding `"type": "module"` in `package.json`.

```js
// math.js — named exports
export function sum(a, b) { return a + b; }
export function subtract(a, b) { return a - b; }

// use.js — named imports
import { sum, subtract } from './math.js';
console.log(sum(4, 5));       // 9
console.log(subtract(9, 3)); // 6
```

Default export:

```js
// math.js
export default function sum(a, b) { return a + b; }

// use.js — can be named anything
import mySum from './math.js';
console.log(mySum(4, 5)); // 9
```

### Comparison

| Feature | CommonJS (`require`) | ES Modules (`import`) |
|---|---|---|
| Syntax | `require()` / `module.exports` | `import` / `export` |
| Default in Node.js | Yes | Requires `"type": "module"` |
| Used in legacy NPM packages | Yes | Increasingly common |
| Dynamic loading | Yes | Static (top of file) |
| Browser support | No | Yes (native) |

## The `fs` Module — File System Operations

The built-in `fs` module allows Node.js to perform **CRUD operations** on the file system (CPU-level operations not possible in the browser).

### Create / Write a file

```js
import fs from 'fs';

// Synchronous (blocking) — waits until done
fs.writeFileSync('rn.txt', 'My name is Aryan');

// Asynchronous (non-blocking) — recommended
fs.writeFile('rn.txt', 'My name is Aryan', (err) => {
  if (err) return console.error(err);
  console.log('File written!');
});
```

### Append to a file (without overwriting)

```js
fs.appendFile('rn.txt', '\nMy name is Kumar\n', (err) => {
  if (err) return console.error(err);
  console.log('Content appended!');
});
// rn.txt now contains both lines
```

> Use `writeFile` to overwrite, `appendFile` to add without erasing existing content — useful for logging user activity or server requests.

### Read a file

```js
fs.readFile('rn.txt', 'utf-8', (err, data) => {
  if (err) return console.error(err);
  console.log(data);
});
```

### Delete (unlink) a file

```js
fs.unlink('abc.txt', (err) => {
  if (err) return console.error(err);
  console.log('File removed!');
});
```

> Files are never truly "deleted" — they are **unlinked** from the directory. The data remains in garbage memory until overwritten. This is why a factory reset needs to be done 3 times to make data unrecoverable.

### CRUD Summary

| Operation | Sync method | Async method |
|---|---|---|
| **Create / Write** | `fs.writeFileSync()` | `fs.writeFile()` |
| **Read** | `fs.readFileSync()` | `fs.readFile()` |
| **Update (append)** | `fs.appendFileSync()` | `fs.appendFile()` |
| **Delete** | `fs.unlinkSync()` | `fs.unlink()` |

## Library vs Framework

A question that often comes up around React and Node:

| | Library | Framework |
|---|---|---|
| **Definition** | Solves a singular problem | Provides end-to-end development tools |
| **Flexibility** | High — you control the structure | Low — follows strict rules |
| **Example** | React (originally) | Next.js, Angular |
| **Analogy** | A cool, flexible person — wear anything | A gentleman's rulebook — follow the rules |

React **started as a library** (solving re-rendering and reconciliation problems) but through extensive adoption and ecosystem growth, it is now widely considered a **framework**.

**Why React borrows everything:**

- Routing → `react-router-dom`
- State management → `react-redux`
- UI components → `shadcn/ui`, `MUI`
- Styling → `tailwindcss`

React itself owns nothing — it borrows through NPM packages.

**Why Next.js is a framework:**

- You can write server-side and client-side code in the same project.
- Server-side components by default.
- End-to-end development without needing a separate backend.

## Why Node.js + MongoDB Go Together

A commonly asked question: why is MongoDB the default database in the MERN stack?

- MongoDB's internal shell (**Mongo Shell**) is written in JavaScript.
- MongoDB's `map`, `filter`, `reduce` operations in the aggregation pipeline are based on JavaScript syntax.
- Node.js and MongoDB share the **same DNA** — JavaScript.
- They are natively compatible, which reduces friction in development.

CouchDB is another database whose `map-reduce` is also written in JavaScript, for the same reason.

## ECMAScript (ES6+) in Node.js

Node.js is built against modern versions of V8 and supports the latest ECMAScript standards. Unlike browsers (where you must wait for users to update), with Node.js you control the version.

ES6 features are split into three groups:

| Group | Status | How to enable |
|---|---|---|
| **Shipping** | Stable, in V8 | On by default — no flags needed |
| **Staged** | Almost complete, not stable | `--harmony` flag |
| **In progress** | Incomplete, experimental | Individual harmony flags (not recommended) |

Check V8 version bundled with Node.js:

```bash
node -p process.versions.v8
```
