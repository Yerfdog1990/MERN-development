# React Hooks

---

## What are Hooks?

**Hooks** are built-in JavaScript functions that let you "hook into" React state and lifecycle features from **functional components**. They eliminate the need for class-based components, allowing you to write cleaner, more modular, and reusable code.

Before hooks existed, React used class components with lifecycle methods (`componentDidMount`, `componentDidUpdate`, etc.). When React moved to functional components, it had nothing to replace that behaviour — so hooks were born as React's generous transfer of that power to functions.

> Hooks are the **middleware** of React. Just like backend middleware intercepts requests to run authentication or logic before a response, hooks intercept component behaviour to add state, side effects, or optimisation.

Everything starting with `use` is a hook: `useState`, `useEffect`, `useRef`, `useContext`, and so on. In Node.js backend middleware uses `use` as well — same concept, different environment.

---

## Golden Rules of Hooks

Before writing any hook, you must follow these two rules:

1. **Only call hooks at the top level** — never inside loops, conditions, or nested functions
2. **Only call hooks from functional components** — not from regular JS functions or class components

```jsx
// BAD — hook inside a condition
if (isLoggedIn) {
  const [user, setUser] = useState(null); // violates rules
}

// GOOD — hook at top level
const [user, setUser] = useState(null);
if (isLoggedIn) {
  // use user here
}
```

## The 15 Essential Hooks

React hooks fall into four categories:

| Category | Hooks |
|---|---|
| **General / State** | `useState`, `useRef` |
| **Lifecycle / Side Effects** | `useEffect`, `useLayoutEffect` |
| **Data Transfer** | `useContext`, `createContext` |
| **Performance / Optimisation** | `useMemo`, `useCallback`, `React.memo`, `memo` |
| **Complex State** | `useReducer` |
| **Navigation** | `useNavigate` |
| **Custom** | Any `useSomething` you build yourself |

> The two legendary hooks that can make any other hook are **`useState`** and **`useEffect`**.

## Hook 1 — `useState`

`useState` manages local reactive state in a component. When the state changes, React automatically re-renders the component to update the UI.

### Syntax

```jsx
const [value, setValue] = useState(initialValue);
//     ^        ^                    ^
// current   updater fn           initial value
```

### Why variables alone fail

```jsx
// Variables do not trigger re-renders — UI stays frozen
function App() {
  let count = 0;

  const handleClick = () => {
    count++;
    console.log(count); // JS updates correctly, but UI never changes
  };

  return (
    <>
      <h1>{count}</h1>
      <button onClick={handleClick}>Increase</button>
    </>
  );
}
```

**The problem:** JS manages the logic. The DOM manages the UI. There is no sync between them without state.

### useState solution

```jsx
import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>You clicked {count} times</p>
      <button onClick={() => setCount(count + 1)}>Click me</button>
    </div>
  );
}
```

Every time `setCount` is called:
1. The state value updates
2. The component re-renders
3. Every instance of `count` in the JSX updates automatically — no `document.querySelector` needed

### Newton's First Law of Components

> A component will **not** re-render until an external force is applied — that force is a state change via the setter function.

### The `useState` Bus Analogy

Think of `useState` as a two-tyre bus:
- **Tyre 1** — the variable holding the value (the bag being carried)
- **Tyre 2** — the setter function (the conductor/driver who delivers updates and triggers reload)

Without the conductor (`setCount`), the bus never moves and the DOM never updates.

## Hook 2 — `useEffect`

`useEffect` lets you synchronise a component with an **external system** — APIs, timers, DOM events, subscriptions. It runs **after** the component renders.

### The Side Effect Problem

Without `useEffect`, every function inside a component reruns on every state change — even if it has nothing to do with that state:

```jsx
function App() {
  const [count, setCount] = useState(0);

  // This runs EVERY time count changes — wasteful if it is an API call
  console.log("function called");

  return (
    <>
      <h1>{count}</h1>
      <button onClick={() => setCount(count + 1)}>Change</button>
    </>
  );
}
```

### Syntax

```jsx
useEffect(() => {
  // side effect code here

  return () => {
    // cleanup code (optional)
  };
}, [dependencies]);
```

### Dependency Array — Controls When the Effect Runs

| Dependency Array | When it runs |
|---|---|
| No array (omitted) | After **every** render |
| Empty array `[]` | **Once** on mount only (FCP — First Contentful Paint) |
| `[dep1, dep2]` | On mount + whenever `dep1` or `dep2` changes |

```jsx
// Run once on mount
useEffect(() => {
  console.log("Component mounted");
}, []);

// Run when count changes
useEffect(() => {
  console.log("Count updated:", count);
}, [count]);

// Run on every render (rarely needed)
useEffect(() => {
  console.log("Any render");
});
```

### Component Lifecycle with `useEffect`

`useEffect` replaces all class-based lifecycle methods:

```jsx
// 1. Mounting — runs once
useEffect(() => {
  console.log("Component mounted");
}, []);

// 2. Updating — runs when dependency changes
useEffect(() => {
  console.log("Component updated");
}, [count]);

// 3. Unmounting — cleanup function
useEffect(() => {
  console.log("Component mounted");

  return () => {
    console.log("Component unmounted — cleanup");
  };
}, []);
```

**Timeline:**

```
Mount   -> effect runs   -> logs "Component mounted"
Update  -> cleanup runs  -> effect runs again
Unmount -> cleanup runs  -> component removed
```

### Common Cleanup Use Cases

```jsx
// Clearing timers
useEffect(() => {
  const timer = setInterval(() => console.log("tick"), 1000);
  return () => clearInterval(timer);
}, []);

// Removing event listeners
useEffect(() => {
  const handleResize = () => console.log(window.innerWidth);
  window.addEventListener("resize", handleResize);
  return () => window.removeEventListener("resize", handleResize);
}, []);

// Cancelling API calls
useEffect(() => {
  const controller = new AbortController();
  fetch(url, { signal: controller.signal })
    .then(res => res.json())
    .then(data => setData(data));
  return () => controller.abort();
}, [url]);
```

### Practical Example — Data Fetching

```jsx
const App = () => {
  const [users, setUsers] = useState([]);

  useEffect(() => {
    fetch("https://jsonplaceholder.typicode.com/users")
      .then(res => res.json())
      .then(data => setUsers(data));
  }, []); // Fetch once on mount

  return (
    <ul>
      {users.map(user => <li key={user.id}>{user.name}</li>)}
    </ul>
  );
};
```

### Common Mistakes with `useEffect`

```jsx
// Infinite loop — sets state inside an effect with no dependency control
useEffect(() => {
  setCount(count + 1); // triggers re-render -> effect runs -> triggers re-render -> infinite loop
});

// Use functional updater to avoid stale closures
useEffect(() => {
  const timer = setInterval(() => {
    setCount(prev => prev + 1); // safe — no dependency on count
  }, 1000);
  return () => clearInterval(timer);
}, []);
```

## Hook 3 — `useLayoutEffect`

`useLayoutEffect` is identical to `useEffect` in syntax but different in **timing**:

| | `useEffect` | `useLayoutEffect` |
|---|---|---|
| Timing | After paint (async) | Before paint (sync) |
| Blocks rendering | No | Yes |
| Use case | Data fetching, subscriptions | DOM measurements, visual updates |
| Performance | Better (non-blocking) | Can cause lag if heavy |

### The Anabolic Steroid Analogy

> `useEffect` = natural training. Performance improves gradually. Sustainable.
> `useLayoutEffect` = steroids. Short-term boost but long-term drawbacks if overused.

React's official documentation even warns: *"useLayoutEffect can hurt performance. Prefer useEffect when possible."*

```jsx
// useLayoutEffect — changes ready BEFORE the browser paints
useLayoutEffect(() => {
  console.log("Runs before browser paints");
  // No flicker, no blank screen, but can hurt performance if heavy
}, [count]);
```

**When to use `useLayoutEffect`:**
- Measuring DOM element dimensions before the user sees the element
- Preventing flicker on position-dependent animations
- Reading and writing to the DOM in the same tick

**When to use `useEffect`:** Everything else — prefer it by default.

## Hook 4 — `useRef`

`useRef` returns a mutable object `{ current: value }`. Changing `.current` does **not** trigger a re-render.

### Two Use Cases

**1. Persisting values between renders (without re-rendering)**

```jsx
function App() {
  const [count, setCount] = useState(0);
  const ref = useRef(0);

  const handleClick = () => {
    setCount(count + 1);
    ref.current = ref.current + 1; // persists between renders, no re-render
    console.log(ref.current); // 1, 2, 3, 4...
  };

  return (
    <>
      <h1>Count: {count}</h1>
      <button onClick={handleClick}>Increment</button>
    </>
  );
}
```

**Why variables fail here:** On every state change, the component re-renders top to bottom and `let value = 0` is reinitialised. `useRef` holds the reference so the value is never lost between renders.

**2. DOM manipulation (accessing DOM elements directly)**

```jsx
import { useRef, useEffect } from 'react';

function InputFocus() {
  const inputRef = useRef(null);
  const headingRef = useRef(null);

  useEffect(() => {
    inputRef.current.focus();
    headingRef.current.style.color = "red";
    // Must be inside useEffect — DOM not available during render phase
  }, []);

  return (
    <>
      <h1 ref={headingRef}>Hello World</h1>
      <input ref={inputRef} type="text" />
    </>
  );
}
```

> **Why use `useEffect` with DOM refs?** JavaScript is parser-blocking. The DOM must be fully painted before JS can access elements. `useEffect` guarantees the DOM is ready before running.

### Controlled vs Uncontrolled Components

| Type | Managed By | Access Method |
|---|---|---|
| **Controlled** | React state (`useState`) | State setter triggers re-render |
| **Uncontrolled** | DOM directly | `useRef` to access DOM node |

```jsx
// Controlled — value driven by state
const [name, setName] = useState('');
<input value={name} onChange={e => setName(e.target.value)} />

// Uncontrolled — value read from DOM via ref
const nameRef = useRef();
<input ref={nameRef} />
// Access: nameRef.current.value
```

Controlled vs uncontrolled component is one of the **most asked machine coding interview questions**.

### `useRef` vs `useState`

| Feature | `useRef` | `useState` |
|---|---|---|
| Triggers re-render | No | Yes |
| Persists across renders | Yes | Yes |
| Mutable | Direct `.current` assignment | Must use setter |
| Best for | DOM access, timers, silent counters | UI-visible data |

## Hook 6 — `useMemo`

`useMemo` **caches (memoises) the return value** of a function. It only recalculates when dependencies change, preventing expensive computations from running on every render.

### The Problem

```jsx
function App() {
  const [count, setCount] = useState(0);

  // Runs on EVERY render — 10 million iterations each click = lag
  function sum() {
    let total = 0;
    for (let i = 0; i < 10_000_000; i++) total += i;
    return total;
  }

  const result = sum(); // recalculates every time count changes
}
```

### The Memoisation Analogy

> What is 3 x 3? You say 9 immediately — not because you calculate it every time, but because you **remember** it. Memoisation works the same way. React stores the result and returns the cached value instead of recalculating, as long as the inputs have not changed.

### `useMemo` Solution

```jsx
import { useState, useMemo } from 'react';

function App() {
  const [count, setCount] = useState(0);

  // Only recalculates when dependencies change
  const result = useMemo(() => {
    console.log("heavy function called");
    let total = 0;
    for (let i = 0; i < 10_000_000; i++) total += i;
    return total;
  }, []); // empty deps = calculate once and remember forever

  return (
    <>
      <h1>Sum: {result}</h1>
      <h1>Count: {count}</h1>
      <button onClick={() => setCount(count + 1)}>Increment</button>
    </>
  );
}
```

Now clicking the button updates `count` instantly — `sum` is not recalculated because its dependency array is empty.

### Practical `useMemo` — Filtering Large Lists

```jsx
function ProductList({ products }) {
  const [filter, setFilter] = useState('');

  const filteredProducts = useMemo(() => {
    return products.filter(p => p.name.includes(filter));
  }, [products, filter]);

  return (
    <div>
      <input value={filter} onChange={e => setFilter(e.target.value)} />
      <ul>{filteredProducts.map(p => <li key={p.id}>{p.name}</li>)}</ul>
    </div>
  );
}
```

## Hook 7 — `React.memo` and `memo`

`React.memo` is a Higher-Order Component that **prevents a child component from re-rendering** if its props have not changed.

### The Problem

```jsx
// Every time parent state changes, Child re-renders unnecessarily
function Child() {
  console.log("child component loaded");
  return <div>Child</div>;
}

function App() {
  const [count, setCount] = useState(0);
  return (
    <>
      <h1>{count}</h1>
      <button onClick={() => setCount(count + 1)}>Change</button>
      <Child /> {/* re-renders on every count change — has no state of its own */}
    </>
  );
}
```

### Solution — Freeze the Component with `React.memo`

```jsx
import { memo } from 'react';

const Child = memo(() => {
  console.log("child component loaded");
  return <div>Child</div>;
});

// OR wrap on export
export default memo(Child);
```

Now `Child` only re-renders when its **own props change**. React's rule: if the state is not changing, do not reload. `memo` enforces this contract.

## Hook 8 — `useCallback`

`useCallback` **caches a function definition** so it maintains the same memory reference across renders.

### Why Functions Cause Re-renders

In JavaScript, functions are first-class citizens. Every render creates a **new function instance** with a new memory address. So even if a memoised child receives "the same function", React sees a different reference and triggers a re-render.

```
Render 1: handleClick -> memory address 0x123
Render 2: handleClick -> memory address 0x456 (different!)
Child sees: "my prop changed" -> re-renders unnecessarily
```

### `useCallback` Solution

```jsx
import { useState, useCallback, memo } from 'react';

const Child = memo(({ handleClick }) => {
  console.log("Child rendered!");
  return <button onClick={handleClick}>Click Me</button>;
});

function Parent() {
  const [count, setCount] = useState(0);
  const [text, setText] = useState("");

  // Same function reference across renders (unless deps change)
  const handleButtonClick = useCallback(() => {
    setCount(prev => prev + 1);
  }, []); // empty deps = function never recreated

  return (
    <div>
      <input value={text} onChange={e => setText(e.target.value)} />
      <p>Count: {count}</p>
      <Child handleClick={handleButtonClick} />
      {/* Child does not re-render when typing in the input */}
    </div>
  );
}
```

### `useMemo` vs `useCallback`

| | `useMemo` | `useCallback` |
|---|---|---|
| Caches | A computed **value** | A **function reference** |
| Returns | Result of calling the function | The function itself |
| Use case | Expensive calculations | Passing callbacks to memoised children |
| Equivalence | `useMemo(() => fn(), deps)` | `useCallback(fn, deps)` |

### The Three Memoisation Techniques Combined

```jsx
// App.jsx
import { useState, useMemo, useCallback } from 'react';
import Child from './Child';

function App() {
  const [count, setCount] = useState(0);
  const [childCount, setChildCount] = useState(0);

  // useMemo — cache the expensive calculation
  const result = useMemo(() => {
    let sum = 0;
    for (let i = 0; i < 10_000_000; i++) sum += i;
    return sum;
  }, []);

  // useCallback — freeze the function definition
  const sayHi = useCallback(() => "Hi from parent!", []);

  return (
    <>
      <h1>Sum: {result}</h1>
      <h1>Count: {count}</h1>
      <button onClick={() => setCount(count + 1)}>Parent Count</button>
      <button onClick={() => setChildCount(childCount + 1)}>Child Count</button>
      <Child count1={childCount} sayHi1={sayHi} />
    </>
  );
}
```

```jsx
// Child.jsx
import { memo } from 'react';

const Child = ({ count1 }) => {
  console.log("child component loaded");
  return <div>Child Count: {count1}</div>;
};

export default memo(Child);
```

### When NOT to Use These Hooks

All three hooks add overhead — memory allocation, dependency comparison. Misused, they make performance **worse**.

```jsx
// DON'T — useMemo for a trivial operation
const value = useMemo(() => 2 + 2, []); // just write: const value = 4;

// DON'T — useCallback on a native HTML element (no benefit)
const handleClick = useCallback(() => console.log("clicked"), []);
<button onClick={handleClick}>Click</button> // <button> ignores reference changes

// DO — useCallback only when child is wrapped in React.memo
<MemoizedChild onClick={handleClick} />
```

> **Rule:** Measure first, optimise second. Only add these hooks when you have a measurable performance problem.

## Custom Hooks

Custom hooks are JavaScript functions whose names start with `use`. They allow you to extract and reuse stateful logic across multiple components.

> Custom hooks are not a special React feature — they are a **convention** that naturally follows from the design of hooks.

### Why Custom Hooks?

- **Code reusability** — share logic between components without repeating
- **Separation of concerns** — keep component files clean
- **Readability** — complex logic is abstracted away
- **Testability** — hooks can be tested independently

### Rules of Custom Hooks

1. **Must start with `use`** — `useFetch`, `useLocalStorage`, `useToggle`
2. **Can call other hooks** inside
3. **Each component gets its own state** — two components using the same hook do not share state
4. **Follow the Rules of Hooks** — only call at the top level

### Custom Hook vs Regular Function

| Feature | Custom Hook | Regular Function |
|---|---|---|
| Starts with `use` | Yes | No |
| Can use React hooks inside | Yes | No |
| Has its own state | Yes | No |
| Re-renders component | Yes | No |

### Building a Custom API Fetch Hook

The two legendary hooks — `useState` and `useEffect` — combined at 50/50 potential can build a complete custom data fetcher:

```jsx
// useFetch.js
import { useState, useEffect } from 'react';

const useFetch = (url) => {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    setLoading(true);
    setError(null);

    fetch(url)
      .then(res => {
        if (!res.ok) throw new Error("Network response was not ok");
        return res.json();
      })
      .then(data => {
        setData(data);
        setLoading(false);
      })
      .catch(err => {
        setError(err.message);
        setLoading(false);
      });
  }, [url]); // re-fetch whenever url changes

  return { data, loading, error };
};

export default useFetch;
```

**Using the custom hook:**

```jsx
import useFetch from './useFetch';

function App() {
  const { data, loading, error } = useFetch("https://dummyjson.com/products");

  if (loading) return <p>Loading...</p>;
  if (error) return <p>Error: {error}</p>;

  return (
    <ul>
      {data.products.map(item => (
        <li key={item.id}>{item.title}</li>
      ))}
    </ul>
  );
}
```

What `useState` contributes: memory to hold the data. What `useEffect` contributes: the async API call triggered on URL change. Together they form a complete custom hook.

### More Custom Hook Examples

**`useLocalStorage` — persist data across page refreshes:**

```jsx
import { useState } from 'react';

const useLocalStorage = (key, initialValue) => {
  const [value, setValue] = useState(() => {
    const stored = localStorage.getItem(key);
    return stored ? JSON.parse(stored) : initialValue;
  });

  const setStoredValue = (newValue) => {
    setValue(newValue);
    localStorage.setItem(key, JSON.stringify(newValue));
  };

  return [value, setStoredValue];
};
```

**`useToggle` — clean boolean flip:**

```jsx
import { useState } from 'react';

const useToggle = (initialValue = false) => {
  const [value, setValue] = useState(initialValue);
  const toggle = () => setValue(prev => !prev);
  return [value, toggle];
};

// Usage
const [isOpen, toggleOpen] = useToggle(false);
```

**`useDebounce` — delay a value update (e.g. search input):**

```jsx
import { useEffect, useState } from 'react';

const useDebounce = (value, delay = 500) => {
  const [debouncedValue, setDebouncedValue] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => {
      setDebouncedValue(value);
    }, delay);

    return () => clearTimeout(timer); // cleanup on value change
  }, [value, delay]);

  return debouncedValue;
};

// Usage — search only fires 500ms after user stops typing
const debouncedSearch = useDebounce(searchQuery, 500);
```

**`useWindowSize` — track window dimensions:**

```jsx
import { useEffect, useState } from 'react';

const useWindowSize = () => {
  const [size, setSize] = useState({
    width: window.innerWidth,
    height: window.innerHeight
  });

  useEffect(() => {
    const handleResize = () => setSize({
      width: window.innerWidth,
      height: window.innerHeight
    });
    window.addEventListener("resize", handleResize);
    return () => window.removeEventListener("resize", handleResize);
  }, []);

  return size;
};
```

### Custom Hook Best Practices

- Name hooks clearly — `useFetch`, `useAuth`, `useForm`
- Return only what is needed — do not expose internal state
- Keep hooks focused — one hook, one concern
- Handle cleanup inside `useEffect` within the hook
- Never start without `use` — the browser and linters depend on it for hook detection

## Hook Learning Roadmap

```
Phase 1 — General Hooks
  useState        -> manage local state
  useRef          -> DOM access + persist values without re-render

Phase 2 — Lifecycle
  useEffect       -> side effects, API calls, subscriptions, timers
  useLayoutEffect -> synchronous DOM updates before browser paint

Phase 3 — Data Transfer
  createContext + useContext -> avoid prop drilling across deep trees

Phase 4 — Performance / Optimisation
  useMemo         -> cache expensive computation results
  React.memo/memo -> freeze component re-renders when props unchanged
  useCallback     -> freeze function definitions passed as props

Phase 5 — Complex State
  useReducer      -> manage complex state machines (like Redux, locally)

Phase 6 — Custom Hooks
  useFetch        -> API fetching pattern
  useLocalStorage -> browser storage persistence
  useDebounce     -> delay state update (search, autocomplete)
  useToggle       -> clean boolean flip
```

## Summary

- Hooks are functions that let functional components access state and lifecycle features — they are the middleware of React
- The two legendary hooks that form the foundation of all others are **`useState`** and **`useEffect`**
- `useState` bridges the gap between JS logic and DOM rendering — creating a permanent sync via the setter function
- `useEffect` controls **when** side effects run — protecting performance from unnecessary reruns with the dependency array
- `useLayoutEffect` runs synchronously **before** the browser paints — use sparingly; prefer `useEffect`
- `useRef` holds references without causing re-renders — used for DOM manipulation and persisting values
- `useContext` eliminates prop drilling — the data teleportation hook
- `useMemo` memoises **values** — avoids recalculating expensive results
- `React.memo` / `memo` memoises **components** — freezes re-renders when props are unchanged
- `useCallback` memoises **functions** — prevents new references from causing unnecessary child re-renders
- **Custom hooks** combine `useState` + `useEffect` to create reusable, single-concern utilities
- Never start a custom hook without `use` — the convention is what makes it a hook
