# React State and Props

---

## Functional Programming vs Object-Oriented Programming

Before diving into React's state system, it helps to understand *why* React chose functional programming over object-oriented programming — because this decision shapes everything about how state and props work.

### Core Comparison

| Feature | Functional Programming (FP) | Object-Oriented Programming (OOP) |
|---|---|---|
| **Primary Unit** | Pure Functions | Objects and Classes |
| **Data & Behaviour** | Separated entirely | Bundled together (Encapsulation) |
| **State Handling** | Stateless and Immutable | Stateful and Mutable |
| **Programming Style** | Declarative ("What" to solve) | Imperative ("How" to solve) |
| **Concurrency** | Naturally thread-safe | Requires locks / synchronisation |
| **`this` keyword** | Not needed | Central and often confusing |

### Key Principles of Functional Programming

- **Pure Functions** — always return the same output for the same input, with zero side effects
- **Immutability** — data cannot be modified; creating a new version is required for updates
- **First-Class Functions** — functions can be passed as arguments or returned from other functions
- **Recursion** — iteration relies on recursive calls rather than `for` / `while` loops

### Key Principles of OOP

- **Encapsulation** — data and methods are bundled together inside objects
- **Inheritance** — new classes inherit from existing parent classes
- **Polymorphism** — same method name behaves differently based on the calling object
- **Abstraction** — complex logic is hidden behind simpler public interfaces

### Code Style Comparison

**Functional approach — pipeline flow:**

```js
const newRecipe = bake(mix(combineIngredients(flour, eggs, milk)));
```

**OOP approach — interacting entities:**

```js
const cake = new Pastry();
cake.addIngredients(flour, eggs, milk);
cake.mix();
cake.bake();
```

### Why React Chose Functions Over Classes

React moved away from class-based components to function-based components because:

- Functions are more flexible — they can be passed, returned, composed, and attached to other functions
- The `this` keyword in classes behaves inconsistently — differently in normal functions, arrow functions, anonymous functions, strict mode, objects, and browser/VS Code environments
- Functions produce less chaotic, more readable code
- Everything React's class system could do — lifecycle, state, inheritance — can be replicated with functions and hooks

> As one senior engineer put it: *"I don't want to deal with the `this` keyword."* — and that summarises why React switched.

Class components still exist and work. You will find them in legacy codebases, and React still uses them for specific things like error boundaries. But **modern React is entirely function-based**.

## Variables vs State

This is the most important distinction to understand before touching `useState`.

### The Core Difference

| Feature | Standard Variable | State |
|---|---|---|
| **Definition** | A container to store and manipulate data | Data a component must "remember" to define its current condition |
| **Re-rendering** | Changes do NOT trigger a UI refresh | Changes trigger a UI re-render to keep screen in sync |
| **Persistence** | Resets every time the component re-runs | Persists across renders |
| **Best Used For** | Temporary calculations, loops, data not shown to user | Interactive elements — counters, modals, form inputs |

### Why Variables Alone Do Not Work in React

```jsx
// ❌ This does NOT update the UI
function App() {
  let a = 10;

  const handleClick = () => {
    a = a + 1;
    console.log(a); // JS updates correctly → 11, 12, 13...
    // But the DOM never re-renders — screen stays at 10
  };

  return (
    <>
      <h1>{a}</h1>
      <button onClick={handleClick}>Increase</button>
    </>
  );
}
```

The console shows the correct value — JavaScript is doing its job. But the screen never updates. Why?

> **JavaScript manages the logic. The DOM manages the UI. There is no automatic sync between them.**

In vanilla JS, you had to manually bridge this gap with `document.querySelector` and `textContent`:

```js
// Vanilla JS — manual, painful for large apps
document.querySelector('#count').textContent = a;
document.querySelector('#para').textContent = a;
// Imagine doing this for 1,000 components...
```

React's solution: **state**. Whenever a state value changes, React automatically reacts and updates every component that uses it — no manual DOM selection required.

### Real-World Examples of State-Driven Behaviour

State dictates how a system looks, responds, and functions at any given moment:

| Context | State Example |
|---|---|
| **Authentication** | Show "Login" button vs user's private dashboard |
| **Dark Mode** | Swap entire app colour scheme between white and black |
| **Loading Spinners** | Show spinner while fetching, replace with content when done |
| **Form Validation** | Disable "Submit" button until email field is valid |
| **E-Commerce Cart** | Update badge count after "Add to Cart" is clicked |
| **Inventory** | Change button from "Buy Now" to "Out of Stock" at zero |
| **Video Games** | Trigger "Game Over" screen when health reaches zero |
| **Thermostats** | Turn AC on when room temperature exceeds 24°C |

## Component Lifecycle

Before functional components and hooks existed, React used **class-based components** with a lifecycle system. Understanding it helps you understand *why* hooks exist.

### Component Lifecycle Phases

A component goes through four phases — like a human life cycle:

```
Initialization → Mounting → Updating → Unmounting
(Conceived)      (Born)     (Growing)   (Dies)
```

| Phase | Class Method | Description |
|---|---|---|
| **Initialization** | Constructor | Component is set up with initial state and props |
| **Mounting** | `componentDidMount` | Component appears on screen for the first time |
| **Updating** | `componentDidUpdate` | Component re-renders due to state or prop change |
| **Unmounting** | `componentWillUnmount` | Component is removed from the screen |

Each phase had "shell / will / did" variations — `shouldComponentUpdate`, `componentWillMount`, `componentDidMount`, etc. — to handle the process before and after each transition.

**Hooks replaced all of this** when React moved to functional components. Instead of lifecycle methods spread across a class, you use one hook — `useEffect` — to handle all lifecycle behaviour.

## `useState` Hook

`useState` is the most fundamental hook in React. It creates a **state variable** — a variable whose change triggers a component re-render.

### Why It Exists

Think of React as a bus service between your JS logic and your DOM:

- The **state variable** is the bag being carried
- The **setter function** (`setState`) is the driver/conductor — the moment you load a new value, it drives the update to the screen and triggers a reload

> Without `useState`, there is no automatic sync between your JS value and what the user sees.

### Basic Syntax

```jsx
import { useState } from 'react';

const [count, setCount] = useState(0);
//     ↑             ↑              ↑
// current value  updater fn    initial value
```

- `count` — the current state value
- `setCount` — the function that updates the value AND triggers a re-render
- `useState(0)` — initialises the state with `0`

**Rule:** Always name the updater as `set` + variable name: `count` → `setCount`, `name` → `setName`, `isOpen` → `setIsOpen`.

### Counter Example

```jsx
import { useState } from 'react';

function App() {
  const [count, setCount] = useState(0);

  return (
    <>
      <h1>{count}</h1>
      <p>{count}</p>  {/* auto-updates everywhere */}

      <button onClick={() => setCount(count + 1)}>Increment</button>
      <button onClick={() => setCount(count - 1)}>Decrement</button>
    </>
  );
}
```

Every time `setCount` is called, React:

1. Updates the state value
2. Re-renders the component
3. Updates **every** instance of `count` on screen automatically

No `document.querySelector`. No `textContent`. No manual DOM updates.

### Newton's First Law of Components

> A component will not re-render until an external force is applied — that force is a state change via the setter function.

Until `setCount` is called, the component stays exactly as it is. **State change = re-render trigger.**

## Props — Passing Data Between Components

**Props** (short for properties) are how you pass data **from a parent component to a child component**. They make components reusable with different values each time they are used.

### Core Rules of Props

- **Unidirectional** — data flows strictly downward: parent → child
- **Read-Only (Immutable)** — a child component must **never** modify its own props
- **Any value allowed** — strings, numbers, booleans, arrays, objects, functions

### The Problem Props Solve

Without props, you would need to create a separate component for every unique piece of data:

```jsx
// ❌ Without props — duplicated for every person
function Card1() {
  return <><h1>My name is Because</h1><h2>My age is 26</h2></>;
}

function Card2() {
  return <><h1>My name is Aryan</h1><h2>My age is 24</h2></>;
}
// 40 students = 40 separate components — violates DRY principle
```

**With props — one component, infinite reuse:**

```jsx
// ✅ With props — one component handles everyone
function Card(props) {
  return (
    <>
      <h1>My name is {props.fullName}</h1>
      <h2>My age is {props.age}</h2>
    </>
  );
}

function App() {
  return (
    <>
      <Card fullName="Because" age={26} />
      <Card fullName="Aryan" age={24} />
      <Card fullName="Spurs" age={27} />
    </>
  );
}
```

### How Props Work Internally

When React sees `<Card fullName="Aryan" age={24} />`, it calls `Card` with a single `props` object:

```js
// What React passes to Card behind the scenes
{ fullName: "Aryan", age: 24 }
```

### Destructuring Props

Instead of writing `props.fullName` and `props.age` everywhere, destructure in the function parameters:

```jsx
// Using props object
function Card(props) {
  return <h1>{props.fullName} is {props.age}</h1>;
}

// Destructured — cleaner and recommended
function Card({ fullName, age }) {
  return <h1>{fullName} is {age}</h1>;
}
```

### Default Prop Values

Assign fallback values directly in the destructured parameters:

```jsx
function UserCard({ username, age = 18 }) {
  return <p>{username} is {age} years old.</p>;
}

// If age is not passed, it defaults to 18
<UserCard username="Aryan" />
```

### The `children` Prop

`props.children` is automatically filled with whatever JSX is placed between your component's opening and closing tags:

```jsx
// Parent
function App() {
  return (
    <Layout>
      <h1>Welcome To My Site</h1>
    </Layout>
  );
}

// Child
function Layout({ children }) {
  return <div className="container">{children}</div>;
}
```

### You Can Pass Functions as Props

Props can carry any JavaScript value — including functions. This is the trick that enables state lifting:

```jsx
function App() {
  const sum = (a, b) => a + b;

  return <Card fullName="Aryan" age={24} calculate={sum} />;
}

function Card({ fullName, age, calculate }) {
  return (
    <>
      <h1>{fullName}</h1>
      <p>Sum of 1 and 1: {calculate(1, 1)}</p>
    </>
  );
}
```

### Props vs State

| Feature | Props | State |
|---|---|---|
| **Source** | Passed by a parent component | Created and managed within the component |
| **Mutability** | Immutable (Read-Only) | Mutable (via setter functions) |
| **Re-renders** | Re-renders if parent updates them | Re-renders directly when updated |
| **Direction** | Parent → Child only | Local to the component |

## State Lifting (Lifting State Up)

### The Problem

React props flow **one way** — parent to child. But what if two sibling components need to share the same data?

```
        App
       /   \
   Child A  Child B    ← siblings cannot share data directly
```

You cannot pass data directly from `Child A` to `Child B`. Props only go downward.

### The Solution — Lift the State to the Common Parent

Move the shared state **up** to the nearest common ancestor. Then pass it **down** to both siblings as props.

```
        App (holds shared state)
       /            \
   Child A        Child B
(sends data up)  (receives data)
```

### The Trick — Pass the Setter Function as a Prop

Instead of trying to reverse the data flow, the parent passes its **setter function** to the child as a prop. The child loads data into it — the parent receives the update automatically.

```
Parent → passes empty container (setName) → Child
Child → loads value into container → State updates in Parent
Parent → re-renders with new value → displays everywhere
```

This is like opening a **joint bank account**. The parent owns the account. The child deposits money into it. The parent sees the balance updated without needing to know the child put it there.

### Full Example — Lifting State Up

**`App.jsx` (Parent — holds the state):**

```jsx
import { useState } from 'react';
import InputComponent from './InputComponent';
import DisplayComponent from './DisplayComponent';

export default function App() {
  const [text, setText] = useState('');

  return (
    <div>
      <h2>Parent Component</h2>
      {/* Pass the setter function DOWN to the child */}
      <InputComponent onTextChange={setText} value={text} />

      {/* Pass the state value DOWN to the display child */}
      <DisplayComponent message={text} />
    </div>
  );
}
```

**`InputComponent.jsx` (Sender child — calls parent's function):**

```jsx
export default function InputComponent({ value, onTextChange }) {
  return (
    <div>
      <label>Type here: </label>
      <input
        type="text"
        value={value}
        onChange={(e) => onTextChange(e.target.value)} // loads value INTO parent's state
      />
    </div>
  );
}
```

**`DisplayComponent.jsx` (Receiver child — reads the prop):**

```jsx
export default function DisplayComponent({ message }) {
  return (
    <div style={{ color: 'blue' }}>
      <strong>Live Preview:</strong> {message || "Nothing typed yet..."}
    </div>
  );
}
```

**Why this works:**

- `App` owns the state (`text`, `setText`)
- `App` passes `setText` down to `InputComponent` — the child loads the value
- `App` passes `text` down to `DisplayComponent` — it displays the latest value
- Both siblings stay in sync through the shared parent — **this is state lifting**

### Benefits of Lifting State Up

- **Single source of truth** — data managed in one central place
- **Predictable flow** — easy to trace data changes back to the parent
- **Reusable components** — children become "dumb" (controlled) components that only render data

### Child to Parent Communication

The same principle applies for general child → parent data passing:

```jsx
// PARENT
function ParentComponent() {
  const [message, setMessage] = useState('');

  const receiveData = (childData) => {
    setMessage(childData);
  };

  return (
    <div>
      <p>Data from Child: {message}</p>
      <ChildComponent sendData={receiveData} />
    </div>
  );
}

// CHILD
function ChildComponent({ sendData }) {
  return (
    <button onClick={() => sendData("Hello from the Child!")}>
      Send Data to Parent
    </button>
  );
}
```

## Prop Drilling — The Problem

**Prop drilling** is when data (props) is passed through multiple layers of nested intermediate components just to reach a deeply nested child. The intermediate components do not use the data — they only pass it along.

```jsx
// App → MiddleComponent → DeepChild
// MiddleComponent does nothing with 'user' — just forwards it

function App() {
  const user = { name: "Alex" };
  return <MiddleComponent user={user} />;
}

function MiddleComponent({ user }) {
  // Doesn't use 'user' — only passes it down
  return (
    <div>
      <h3>Middle Component</h3>
      <DeepChild user={user} />
    </div>
  );
}

function DeepChild({ user }) {
  return <p>Welcome back, {user.name}!</p>;
}
```

### Why Prop Drilling Becomes a Problem

| Problem | Description |
|---|---|
| **Maintenance Overhead** | Renaming a prop requires updating every component in the chain |
| **Code Clutter** | Intermediate components become polluted with props they don't use |
| **Reduced Reusability** | Components become tightly coupled to specific data structures |
| **Bug-Prone** | Any component failing to pass props correctly breaks deeply nested components |
| **Performance** | Causes unnecessary re-renders of components that don't even use the props |

> Think of it like passing a water bottle along a row of students. If any one of them refuses or forgets, the bottle never reaches its destination.

---

## Solutions to Prop Drilling

### Solution 1 — Component Composition (Cleanest First Step)

Before reaching for state management tools, restructure components using `children`:

```jsx
function App() {
  const user = { name: "Alex" };
  return (
    <MiddleComponent>
      <DeepChild user={user} />  {/* passed directly — no drilling */}
    </MiddleComponent>
  );
}

function MiddleComponent({ children }) {
  return (
    <div>
      <h3>Middle Component</h3>
      {children}  {/* renders DeepChild without knowing about 'user' */}
    </div>
  );
}
```

## Context API

The **Context API** is React's built-in solution for sharing global data across the component tree **without prop drilling**. It acts as a broadcast network — a provider sends data, and any deep child can tune in and read it directly.

Think of it as hiring a **postman**: the postman takes your data, travels the same hierarchy, but does not disturb any intermediate component. Whoever calls the postman gets the data directly.

### Three Building Blocks

| Concept | Purpose |
|---|---|
| `createContext()` | Creates a new Context object — the "postman" |
| `<Context.Provider value={...}>` | Wraps the component tree and provides the shared data |
| `useContext(Context)` | Used by any child to read the context value directly |

### Step-by-Step — Theme Toggle Example

**Step 1 — Create the Context:**

```js
// ThemeContext.js
import { createContext } from 'react';

export const ThemeContext = createContext('light'); // default fallback value
```

**Step 2 — Provide the Context:**

```jsx
// App.jsx
import { useState } from 'react';
import { ThemeContext } from './ThemeContext';
import Dashboard from './Dashboard';

export default function App() {
  const [theme, setTheme] = useState('dark');

  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      <Dashboard />  {/* All nested components can now access theme and setTheme */}
    </ThemeContext.Provider>
  );
}
```

**Step 3 — Consume the Context:**

```jsx
// ThemeButton.jsx
import { useContext } from 'react';
import { ThemeContext } from './ThemeContext';

export default function ThemeButton() {
  const { theme, setTheme } = useContext(ThemeContext); // grabs data directly

  return (
    <button
      onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}
      style={{ backgroundColor: theme === 'dark' ? '#000' : '#fff' }}
    >
      Toggle to {theme === 'light' ? 'dark' : 'light'} Mode
    </button>
  );
}
```

No props passed through `Dashboard`. No intermediate components touched. The data goes straight from `App` to `ThemeButton`.

### Full Prop Drilling Fix — Counter Example

**Without Context API (prop drilling):**

```jsx
// Parent → Child → GrandChild
// Child doesn't use count — just passes it
function ParentComponent() {
  const [count, setCount] = useState(0);
  return <ChildComponent count={count} setCount={setCount} />;
}

function ChildComponent({ count, setCount }) {
  return <GrandChildComponent count={count} setCount={setCount} />;
}

function GrandChildComponent({ count, setCount }) {
  return (
    <>
      <h3>Count: {count}</h3>
      <button onClick={() => setCount(count + 1)}>Increase</button>
    </>
  );
}
```

**With Context API (no drilling):**

```jsx
// counterContext.js
import { createContext, useState } from 'react';

const CounterContext = createContext({ count: 0, setCount: () => {} });

const CounterProvider = ({ children }) => {
  const [count, setCount] = useState(0);

  return (
    <CounterContext.Provider value={{ count, setCount }}>
      {children}
    </CounterContext.Provider>
  );
};

export { CounterContext, CounterProvider };
```

```jsx
// main.jsx — wrap the app
import { CounterProvider } from './counterContext';
createRoot(document.getElementById('root')).render(
  <CounterProvider><App /></CounterProvider>
);
```

```jsx
// GrandChildComponent.jsx — consume directly
import { useContext } from 'react';
import { CounterContext } from './counterContext';

function GrandChildComponent() {
  const { count, setCount } = useContext(CounterContext);

  return (
    <>
      <h3>Count: {count}</h3>
      <button onClick={() => setCount(count + 1)}>Increase</button>
    </>
  );
}
```

`ChildComponent` now has no mention of `count` or `setCount`. Clean, decoupled, and maintainable.

### Custom Hook Pattern (Best Practice)

Wrap `useContext` in a custom hook for reusability and cleaner error handling:

```jsx
// counterContext.js
export const useCounter = () => {
  const context = useContext(CounterContext);
  if (!context) {
    throw new Error('useCounter must be used inside CounterProvider');
  }
  return context;
};

// Usage in any component
const { count, setCount } = useCounter();
```

### Memoise Context Values (Performance Best Practice)

Prevent unnecessary re-renders of consuming components by memoising the context value:

```jsx
import { useMemo } from 'react';

const CounterProvider = ({ children }) => {
  const [count, setCount] = useState(0);

  const value = useMemo(() => ({ count, setCount }), [count]);

  return (
    <CounterContext.Provider value={value}>
      {children}
    </CounterContext.Provider>
  );
};
```

### When to Use Context API

| Use Case | Good Fit? |
|---|---|
| Theme (light / dark mode) | Yes |
| User authentication state | Yes |
| Language / localisation | Yes |
| Notification settings | Yes |
| Rapidly updating data (text fields, game loops) | No — causes excessive re-renders |
| Very large global state | No — use Redux / Zustand instead |

### Context API Limitations

- **Re-render cascade** — every consuming component re-renders when the context value changes, even if only a slice of data changed
- **Not for high-frequency updates** — chat input, game state, live data streams should use local state
- **Data size** — like a postman, it is built for parcels, not cars. Large or complex global state needs Redux

## State Management — Choosing the Right Tool

| Tool | Best For | Scale |
|---|---|---|
| `useState` | Local component state | Small |
| Props + State Lifting | Sharing between 2–3 components | Small–Medium |
| Context API | Global low-frequency state (auth, theme) | Medium |
| Redux Toolkit | Complex, large, frequently updating global state | Large |
| Zustand | Lightweight global state, simpler than Redux | Medium–Large |
| MobX | Observable-driven reactive state | Medium–Large |

### Redux — Quick Overview

Redux stores all application state in a single **store** — a central source of truth. Components read from and write to this store directly, eliminating prop drilling entirely.

**Core Redux Concepts:**

| Concept | Description |
|---|---|
| **Store** | Single source of truth — holds the entire state tree |
| **Actions** | Plain JS objects with a `type` field — describe what happened |
| **Reducers** | Pure functions that receive state + action, return new state |
| **Slices (RTK)** | Bundles initial state, reducers, and action creators together |

**Install:**

```bash
npm install @reduxjs/toolkit react-redux
```

**Create a slice:**

```js
// src/features/counterSlice.js
import { createSlice } from '@reduxjs/toolkit';

const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    increment: (state) => { state.value += 1; },
    decrement: (state) => { state.value -= 1; },
  },
});

export const { increment, decrement } = counterSlice.actions;
export default counterSlice.reducer;
```

**When to choose Redux over Context API:**

- Application state is large and complex
- State updates happen very frequently
- Multiple developers need a predictable, debuggable data flow
- You need time-travel debugging via Redux DevTools

## Summary

| Concept | Key Takeaway |
|---|---|
| **FP vs OOP** | React uses functions for less chaos, better reusability, and no `this` confusion |
| **Variable vs State** | Variables don't re-render the UI; state does — use `useState` for anything displayed |
| **`useState`** | Creates a state variable + setter function; setter triggers re-render |
| **Props** | Pass data parent → child; immutable; any JS value allowed |
| **Prop Destructuring** | `{ fullName, age }` instead of `props.fullName` — cleaner |
| **`children` Prop** | Special prop — whatever is placed between component tags |
| **State Lifting** | Move shared state to nearest common parent; pass setter down to child |
| **Child → Parent** | Pass a callback function as a prop; child calls it with data |
| **Prop Drilling** | Passing props through intermediate components that don't need them — avoid past 2–3 levels |
| **Context API** | Teleport data to any deep component; avoid for high-frequency updates |
| **Redux / Zustand** | Global state managers for large-scale, complex, frequently updated state |
