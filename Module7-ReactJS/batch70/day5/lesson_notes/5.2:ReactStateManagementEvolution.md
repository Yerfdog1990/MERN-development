# Evolution of React State Management

React's approach to managing state has changed dramatically since its release in 2013. This document traces that evolution — from `this.state` in class components to modern atomic and server-state libraries — with syntax and code examples at each stage.

---

## 1. The Beginning: Class Component `this.state` (2013–2018)

Before Hooks, state could only live inside **class components**. Function components were "dumb" — they could only receive props and render UI.

### Syntax

```jsx
import React, { Component } from 'react';

class Counter extends Component {
  constructor(props) {
    super(props);
    this.state = { count: 0 };
  }

  increment = () => {
    this.setState({ count: this.state.count + 1 });
    // or, safer with functional updates:
    // this.setState(prevState => ({ count: prevState.count + 1 }));
  };

  render() {
    return (
      <div>
        <p>Count: {this.state.count}</p>
        <button onClick={this.increment}>+1</button>
      </div>
    );
  }
}

export default Counter;
```

### Problems with this approach

- **Boilerplate**: constructors, `super(props)`, binding `this` in event handlers.
- **Prop drilling**: passing state/functions down through many layers of components that don't need them, just to reach a deeply nested child.
- **`this` confusion**: a constant source of bugs (`this` inside callbacks not referring to the component).
- **No easy way to share stateful logic** between components — the only tool was **Higher-Order Components (HOCs)** or **render props**, both of which caused "wrapper hell."

### Render Props (a workaround for sharing logic)

```jsx
class MouseTracker extends Component {
  state = { x: 0, y: 0 };
  handleMove = (e) => this.setState({ x: e.clientX, y: e.clientY });

  render() {
    return (
      <div onMouseMove={this.handleMove}>
        {this.props.render(this.state)}
      </div>
    );
  }
}

// Usage
<MouseTracker render={({ x, y }) => <p>{x}, {y}</p>} />
```

## 2. Context API (React 16.3, 2018) — Solving Prop Drilling

Context introduced a way to pass data through the component tree **without manually passing props at every level**.

### Syntax

```jsx
import React, { createContext, useContext, useState } from 'react';

// 1. Create a context
const ThemeContext = createContext();

// 2. Provide it at the top of the tree
function App() {
  const [theme, setTheme] = useState('light');
  return (
    <ThemeContext.Provider value={{ theme, setTheme }}>
      <Toolbar />
    </ThemeContext.Provider>
  );
}

// 3. Consume it anywhere below, no matter how deep
function Toolbar() {
  return <ThemedButton />;
}

function ThemedButton() {
  const { theme, setTheme } = useContext(ThemeContext);
  return (
    <button onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}>
      Current theme: {theme}
    </button>
  );
}
```

### Limitation

Context solves **prop drilling**, but it's not a full state-management solution:
- Any update to the context value **re-renders every consumer**, even if they only care about part of the value.
- No built-in way to handle async logic, middleware, or derived state efficiently.

## 3. Redux (2015, dominant ~2016–2020) — Centralized, Predictable State

Redux borrowed ideas from Flux and functional programming: a **single store**, **pure reducer functions**, and **actions** describing "what happened."

### Core principles
1. Single source of truth (one store)
2. State is read-only — changed only via dispatched actions
3. Changes are made with pure reducer functions

### Syntax (classic Redux)

```js
// actions.js
export const increment = () => ({ type: 'INCREMENT' });
export const decrement = () => ({ type: 'DECREMENT' });

// reducer.js
const initialState = { count: 0 };

function counterReducer(state = initialState, action) {
  switch (action.type) {
    case 'INCREMENT':
      return { ...state, count: state.count + 1 };
    case 'DECREMENT':
      return { ...state, count: state.count - 1 };
    default:
      return state;
  }
}

export default counterReducer;

// store.js
import { createStore } from 'redux';
import counterReducer from './reducer';

const store = createStore(counterReducer);
export default store;
```

### Connecting to React (via `react-redux`)

```jsx
import { Provider, useSelector, useDispatch } from 'react-redux';
import store from './store';
import { increment, decrement } from './actions';

function Counter() {
  const count = useSelector((state) => state.count);
  const dispatch = useDispatch();

  return (
    <div>
      <p>{count}</p>
      <button onClick={() => dispatch(increment())}>+1</button>
      <button onClick={() => dispatch(decrement())}>-1</button>
    </div>
  );
}

function App() {
  return (
    <Provider store={store}>
      <Counter />
    </Provider>
  );
}
```

### Problems

- **Massive boilerplate**: action types, action creators, reducers, and dispatch wiring for even simple state.
- Async logic required extra middleware (`redux-thunk`, `redux-saga`).
- Steep learning curve for beginners.

### Redux Toolkit (RTK, 2019) — Modernizing Redux

Redux Toolkit was created to fix Redux's boilerplate problem, using `createSlice` to auto-generate action creators and use "mutable-looking" code (powered by Immer under the hood).

```js
// counterSlice.js
import { createSlice } from '@reduxjs/toolkit';

const counterSlice = createSlice({
  name: 'counter',
  initialState: { count: 0 },
  reducers: {
    increment: (state) => {
      state.count += 1; // looks mutable, but Immer makes it immutable
    },
    decrement: (state) => {
      state.count -= 1;
    },
  },
});

export const { increment, decrement } = counterSlice.actions;
export default counterSlice.reducer;

// store.js
import { configureStore } from '@reduxjs/toolkit';
import counterReducer from './counterSlice';

export const store = configureStore({
  reducer: { counter: counterReducer },
});
```

Usage in components stayed the same (`useSelector` / `useDispatch`), but the amount of code to write dropped drastically.

## 4. React Hooks (React 16.8, 2019) — State in Function Components

Hooks let function components hold state and side effects, removing the need for classes entirely for most use cases.

### `useState`

```jsx
import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
      <button onClick={() => setCount(prev => prev - 1)}>-1</button>
    </div>
  );
}
```

### `useReducer` (Redux-like logic, locally)

```jsx
import { useReducer } from 'react';

function reducer(state, action) {
  switch (action.type) {
    case 'increment':
      return { count: state.count + 1 };
    case 'decrement':
      return { count: state.count - 1 };
    default:
      throw new Error('Unknown action');
  }
}

function Counter() {
  const [state, dispatch] = useReducer(reducer, { count: 0 });

  return (
    <div>
      <p>{state.count}</p>
      <button onClick={() => dispatch({ type: 'increment' })}>+1</button>
      <button onClick={() => dispatch({ type: 'decrement' })}>-1</button>
    </div>
  );
}
```

### Custom Hooks — reusable stateful logic without wrapper hell

```jsx
// useCounter.js
import { useState, useCallback } from 'react';

function useCounter(initial = 0) {
  const [count, setCount] = useState(initial);
  const increment = useCallback(() => setCount(c => c + 1), []);
  const decrement = useCallback(() => setCount(c => c - 1), []);
  return { count, increment, decrement };
}

// Usage
function Counter() {
  const { count, increment, decrement } = useCounter(0);
  return (
    <div>
      <p>{count}</p>
      <button onClick={increment}>+1</button>
      <button onClick={decrement}>-1</button>
    </div>
  );
}
```

Hooks made **Context + `useReducer`** a viable lightweight alternative to Redux for many apps.

### Context + useReducer as a "mini-Redux"

```jsx
import { createContext, useContext, useReducer } from 'react';

const CartContext = createContext();

function cartReducer(state, action) {
  switch (action.type) {
    case 'ADD_ITEM':
      return [...state, action.payload];
    case 'REMOVE_ITEM':
      return state.filter(item => item.id !== action.payload);
    default:
      return state;
  }
}

export function CartProvider({ children }) {
  const [cart, dispatch] = useReducer(cartReducer, []);
  return (
    <CartContext.Provider value={{ cart, dispatch }}>
      {children}
    </CartContext.Provider>
  );
}

export function useCart() {
  return useContext(CartContext);
}

// Usage anywhere in the tree
function CartIcon() {
  const { cart } = useCart();
  return <div>Cart ({cart.length})</div>;
}
```

## 5. Lightweight State Libraries (2020–present)

As Hooks matured, a new generation of libraries emerged that avoided Redux's ceremony while staying outside React's re-render tree for better performance.

### Zustand — minimal, hook-based, no boilerplate

```jsx
// store.js
import { create } from 'zustand';

const useCartStore = create((set) => ({
  cart: [],
  addItem: (item) => set((state) => ({ cart: [...state.cart, item] })),
  removeItem: (id) =>
    set((state) => ({ cart: state.cart.filter((i) => i.id !== id) })),
}));

export default useCartStore;

// Component.jsx
function CartIcon() {
  const cart = useCartStore((state) => state.cart);
  return <div>Cart ({cart.length})</div>;
}

function AddButton({ item }) {
  const addItem = useCartStore((state) => state.addItem);
  return <button onClick={() => addItem(item)}>Add to cart</button>;
}
```

No `<Provider>` wrapper needed, and components only re-render when the specific slice of state they select changes.

### Jotai — atomic state (bottom-up, inspired by Recoil)

```jsx
import { atom, useAtom } from 'jotai';

const cartAtom = atom([]);

function CartIcon() {
  const [cart] = useAtom(cartAtom);
  return <div>Cart ({cart.length})</div>;
}

function AddButton({ item }) {
  const [, setCart] = useAtom(cartAtom);
  return (
    <button onClick={() => setCart((prev) => [...prev, item])}>
      Add
    </button>
  );
}
```

Atoms are independent units of state — components subscribe only to the atoms they read, avoiding unnecessary re-renders without needing selectors.

### Recoil (Meta, experimental) — similar atomic model

```jsx
import { atom, useRecoilState } from 'recoil';

const cartState = atom({
  key: 'cartState',
  default: [],
});

function CartIcon() {
  const [cart] = useRecoilState(cartState);
  return <div>Cart ({cart.length})</div>;
}
```

## 6. Separating "Server State" from "Client State" (2020–present)

A major shift in thinking: most app state isn't really *UI* state — it's a **local cache of server data** (API responses). Treating it like Redux state (manually storing, invalidating, refetching) caused a lot of pain. This gave rise to **server-state libraries**.

### React Query (TanStack Query)

```jsx
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';

function CartIcon() {
  const { data: cart, isLoading } = useQuery({
    queryKey: ['cart'],
    queryFn: () => fetch('/api/cart').then((res) => res.json()),
  });

  if (isLoading) return <div>Loading...</div>;
  return <div>Cart ({cart.length})</div>;
}

function AddButton({ item }) {
  const queryClient = useQueryClient();
  const mutation = useMutation({
    mutationFn: (newItem) =>
      fetch('/api/cart', { method: 'POST', body: JSON.stringify(newItem) }),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ['cart'] }),
  });

  return <button onClick={() => mutation.mutate(item)}>Add</button>;
}
```

React Query handles caching, background refetching, retries, and stale-data invalidation automatically — logic that used to be hand-rolled with `useEffect` + `useState` + Redux thunks.

### SWR (Vercel) — a lighter alternative

```jsx
import useSWR from 'swr';

const fetcher = (url) => fetch(url).then((res) => res.json());

function CartIcon() {
  const { data: cart, isLoading } = useSWR('/api/cart', fetcher);
  if (isLoading) return <div>Loading...</div>;
  return <div>Cart ({cart.length})</div>;
}
```

**Key mental model shift**: modern React apps typically split state into:
| Type | Example | Tool |
|---|---|---|
| Server state | cart items, user profile, product list | React Query / SWR |
| Global UI/client state | theme, modal open/closed, auth token | Zustand / Jotai / Context |
| Local component state | input value, hover state | `useState` |

## 7. React 18 (2022) — Concurrent Rendering-Aware State

React 18 didn't introduce a new state management pattern, but added hooks that make state updates **concurrent-rendering aware**.

### `useTransition` — mark updates as non-urgent

```jsx
import { useState, useTransition } from 'react';

function SearchResults() {
  const [query, setQuery] = useState('');
  const [isPending, startTransition] = useTransition();

  function handleChange(e) {
    const value = e.target.value;
    setQuery(value); // urgent: keep the input responsive
    startTransition(() => {
      // non-urgent: can be interrupted by more urgent updates
      searchProducts(value);
    });
  }

  return (
    <>
      <input onChange={handleChange} />
      {isPending && <span>Updating...</span>}
    </>
  );
}
```

### `useSyncExternalStore` — the hook that powers Zustand/Redux under the hood

```jsx
import { useSyncExternalStore } from 'react';

function useCart(store) {
  return useSyncExternalStore(store.subscribe, store.getSnapshot);
}
```

This hook standardized how external stores (Redux, Zustand, Jotai) safely subscribe to state outside React while staying compatible with concurrent rendering.

## 8. React 19 (2024) — Built-in Server State Primitives

React 19 pulled some patterns that used to require libraries directly into core React.

### `use()` — reading promises/context directly in render

```jsx
import { use, Suspense } from 'react';

function CartIcon({ cartPromise }) {
  const cart = use(cartPromise); // suspends until resolved
  return <div>Cart ({cart.length})</div>;
}

function App() {
  const cartPromise = fetch('/api/cart').then((res) => res.json());
  return (
    <Suspense fallback={<div>Loading...</div>}>
      <CartIcon cartPromise={cartPromise} />
    </Suspense>
  );
}
```

### `useActionState` and Form Actions — built-in mutation state

```jsx
import { useActionState } from 'react';

async function addToCartAction(prevState, formData) {
  const itemId = formData.get('itemId');
  const res = await fetch('/api/cart', {
    method: 'POST',
    body: JSON.stringify({ itemId }),
  });
  return res.ok ? { success: true } : { success: false };
}

function AddButton() {
  const [state, formAction, isPending] = useActionState(addToCartAction, null);

  return (
    <form action={formAction}>
      <input type="hidden" name="itemId" value="123" />
      <button type="submit" disabled={isPending}>
        {isPending ? 'Adding...' : 'Add to cart'}
      </button>
      {state?.success && <p>Added!</p>}
    </form>
  );
}
```

This reduces the need for manually tracking loading/error state for mutations, something React Query and Redux Toolkit previously handled.

## Timeline Summary

| Era | Approach | Key Tool(s) |
|---|---|---|
| 2013–2018 | Class `this.state`, HOCs, render props | React core |
| 2015–2020 | Centralized store, actions, reducers | Redux |
| 2018 | Avoiding prop drilling | Context API |
| 2019 | State in function components | Hooks (`useState`, `useReducer`) |
| 2019+ | Less Redux boilerplate | Redux Toolkit |
| 2020+ | Lightweight, selector-based global state | Zustand, Jotai, Recoil |
| 2020+ | Server state as cache, not app state | React Query, SWR |
| 2022 | Concurrent-safe external state | `useTransition`, `useSyncExternalStore` |
| 2024+ | Built-in async/server state primitives | `use()`, `useActionState`, Server Components |

---

## Key Takeaway

The overall trend has been:
1. **From imperative to declarative** state updates.
2. **From centralized-and-heavy to decentralized-and-light** (Redux → Zustand/Jotai).
3. **From treating all state the same to splitting server state from client state** (React Query/SWR vs. Zustand/Context).
4. **From library-land to React core** — patterns proven useful in the ecosystem (external store subscriptions, async state, atoms) are steadily being absorbed into React itself.
