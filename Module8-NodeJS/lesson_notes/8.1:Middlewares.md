# Express.js Middleware 

## 1. Request–Response Cycle Recap

- Client (**System A**) sends a **request** → Server (**System B**) sends a **response** (usually JSON).
- Before the actual request, the browser sends a **preflight request** — a virtual request with no body — to check that everything is OK (CORS, allowed methods, headers). Only after that does the real request (with body) go through.

### HTTP Methods — "Respect the Method"

| Method | Purpose |
|---|---|
| `GET` | Fetch/read data (no body allowed) |
| `POST` | Send data to the server for processing/creation |
| `PUT` | Update an existing resource (recommended over PATCH) |
| `PATCH` | Partial update (not generally recommended) |
| `DELETE` | Delete/unsync a resource |
| `QUERY` (new) | Newly proposed HTTP method — GET-like fetching **with a body** attached |

- `GET` cannot carry a body → filtering is done via **query params** (`req.query.category`) or **route params** (`req.params.id`).
- Status codes are standards (e.g., `201` for created). Follow them; inventing your own creates chaos.

### Client–Server Architecture

- A and B are **independent entities** → **loosely coupled** (temporarily connected only to exchange data).
- **Tightly coupled** systems are bound together, dependent on each other, and cannot switch resources (A couldn't connect to C).
- Loose coupling enforces **separation of concern** — the core rule of client-server architecture.
- **REST** is not a protocol; it is an **architectural design pattern** — a set of rules/constraints. Follow them and your system may be called RESTful (like needing an MBBS degree to call yourself a doctor).
- You *could* do everything through POST (brute force), but delegating tasks to purpose-built methods keeps code modular and optimal.

## 2. What Is Middleware?

**Problem:** Requests reach the server without any check — not even basic sanity checks (is the password null? is the email present?). Making the server process a bad request fully before rejecting it is a **performance overkill**.

**Solution:** Put an entity *between* request and response — a **middleman** = **middleware**.

> Middleware are functions (user-written or npm-installed) that sit between the request and the response, with access to three things:
>
> 1. the incoming **request** (`req`)
> 2. the outgoing **response** (`res`)
> 3. a **`next`** pointer — after the sanity check passes, it decides whether the request proceeds

```js
// Middleware signature
(req, res, next) => {
  // any logic, e.g.
  if (req.body.age >= 18) next();  // pass to the next checkpoint
  else res.end("Not allowed");     // terminate the cycle
}
```

### The 4 Capabilities of Middleware (Express docs)

1. **Execute any code** (fully customizable logic).
2. **Make changes to the request and response objects** (you have access → you can manipulate, like DOM manipulation).
3. **End the request–response cycle** (condition failed → terminate: "You are not a valid user, go back").
4. **Call the next middleware** in the stack via `next()`.

### Bank/Concert Analogy

- Bank account opening: fill a form → counter 1 verifies it → only then points you to counter 2. Counter 2 **trusts** counter 1's work — no re-checking.
- Concert: tickets are checked at the **entry gate**, not inside — that's why middleware is placed **at the top, before routes**.
- **Middleware chaining / stack:** multiple middleware in a row, each with one specific job, each independent. The output of one acts as input for the next.

### The 5 Types of Middleware

1. **Application-level** — `app.use(...)` / `app.METHOD(...)`
2. **Router-level** — attached to an `express.Router()` or written inline as a third argument on a route
3. **Error-handling** — signature `(err, req, res, next)`, placed at the **bottom** of the app
4. **Built-in** — `express.json()`, `express.urlencoded()`, `express.static()`
5. **Third-party** — `helmet`, `cors`, `morgan`, `multer`, `nodemailer`, `cookie-parser`, `passport`, etc.

> Placement rule: all middleware go at the **top** (before routes) — **except error-handling middleware, which goes at the bottom** (after routes), because errors are generated *by* routes.

## 3. Setup — Basic Server

```js
// middleware.js
import express from "express";

const app = express();
const PORT = 8000;

app.get("/", (req, res) => {
  res.end("Hi"); // public route — no check at all
});

app.listen(PORT, () => {
  console.log("Server is running");
});
```

## 4. Application-Level Middleware

```js
app.use((req, res, next) => {
  console.log("Middleware 1 called");
  next(); // REQUIRED — otherwise the request hangs
});

app.get("/", (req, res) => {
  res.end("Hi");
});
```

### The "Orphan API" problem

If you forget `next()`:

- The middleware logic runs (console prints), but the response never arrives.
- The request sits in a **timeout zone** — like a guard who checks you but never tells you where to go.
- Such an API — with no management/parent pointing it forward — is informally called an **orphan API**.

### Stacking multiple middleware

```js
app.use((req, res, next) => {
  console.log("Middleware 1 called");
  next();
});

app.use((req, res, next) => {
  console.log("Middleware 2 called");
  next(); // remove this → orphan again: "1 called", "2 called", but no "Hi"
});

app.get("/", (req, res) => res.end("Hi"));
```

Order of execution: **top to bottom**. Every request passes through the full stack before hitting the route.

## 5. Built-in Middleware — Body Parsing

A POST body arrives as `undefined` unless something parses it:

```js
app.post("/login", (req, res) => {
  console.log(req.body); // undefined — no one parsed the body!
  res.end("Login done");
});
```

Fix — Express ships with built-in parsers (Node.js alone does not; one reason we use Express):

```js
app.use(express.json());                          // parse JSON bodies
app.use(express.urlencoded({ extended: true }));  // parse form-urlencoded bodies
```

Now `req.body` contains `{ username: "...", password: "..." }`.

## 6. Custom Middleware — Credential Check (Auth Sanity Check)

Fake "database" + a middleware that validates credentials **before** the route runs:

```js
import express from "express";
import fs from "fs";

const app = express();
app.use(express.json());

// pretend database
let username = "bekas";
let password = "bekas123";

// custom middleware — sits between request and response
app.use((req, res, next) => {
  if (req.body.username === username && req.body.password === password) {
    console.log("I am done with check, you can go ahead");
    next();
  } else {
    res.end("Invalid credentials");
  }
});

app.post("/login", (req, res) => {
  // serve an actual page instead of plain text
  fs.readFile("home.html", "utf-8", (err, data) => {
    if (err) {
      return res.status(404).json({ message: "Something went wrong" });
    }
    res.send(data);
  });
});

app.listen(8000, () => console.log("Server is running"));
```

```html
<!-- home.html -->
<h1>Welcome to my home page</h1>
```

Behavior:

- Wrong/missing username or password → `Invalid credentials` (cycle **ended** by middleware).
- Correct credentials → `next()` → route runs → HTML served.

### Splitting checks across stacked middleware

Each middleware does **one** job and trusts the previous one:

```js
// Middleware 1 — emptiness check only
app.use((req, res, next) => {
  if (req.body.username === "") {
    res.end("Please enter valid username first"); // end the cycle
  } else {
    next();
  }
});

// Middleware 2 — credential match only (no need to re-check emptiness)
app.use((req, res, next) => {
  if (req.body.username === username && req.body.password === password) {
    next();
  } else {
    res.end("Invalid credentials");
  }
});
```

If a request reaches middleware 2, middleware 1 is already satisfied — that's the trust model of the middleware stack.

## 7. Custom Logger Middleware (Interview Favorite)

*"Build a middleware that logs which user hit which route at what time"* — like a society gate register.

Placed **after** the auth middlewares (so it only logs verified users — no re-checking needed):

```js
import fs from "fs";

// Middleware 3 — logger / ledger
app.use((req, res, next) => {
  const log = `${req.body.username} was accessing ${req.url} at ${Date.now()}\n`;

  // appendFile, NOT writeFile — writeFile overwrites the previous entries
  fs.appendFile("log.txt", log, (err) => {
    next(); // forward regardless
  });
});
```

Useful request properties available inside any middleware:

- `req.method` — GET/POST/...
- `req.url` — route accessed
- `req.body` — payload
- `req.ip` — client IP → basis for **IP-based rate limiting** (e.g., Instagram's "change username once per 45 days", DDoS protection, typically done with **Redis**)

Why logs matter: on Vercel/Netlify/Render/Railway/Heroku, debugging always starts with *"show me the log"* — logs tell you when the system was up/down and which route broke.

## 8. Error-Handling Middleware

- Signature has **four** arguments — `err` comes **first**.
- Must be registered **at the bottom of the application, after all routes** (an error handler can only catch errors from routes above it).

```js
// ... all routes above ...

app.use((err, req, res, next) => {
  console.error(err.stack);           // the error stack — crucial for diagnosis
  res.status(500).send("Something broke!");
});
```

### Why a central error handler + error stack?

- If every route handles its own error its own way ("something went wrong", "hi I broke"), there is **no standard protocol** — like every route having its own try/catch (violates DRY / no singleton pattern).
- The **error stack** is like a full list of symptoms for a doctor: an error surfacing in one route may originate layers below (like a bottom React component breaking because of bad props from the top). Without the stack you diagnose the wrong route.
- The three essentials to report: `err.stack`, `err.message`, `err.statusCode`. Writing these 3 lines in every route violates **DRY** → so create a reusable **ApiError utility class** and pair it with the error middleware:

```js
// utils/ApiError.js
class ApiError extends Error {
  constructor(statusCode, message = "Something went wrong", stack = "") {
    super(message);
    this.statusCode = statusCode;
    if (stack) this.stack = stack;
    else Error.captureStackTrace(this, this.constructor);
  }
}
export default ApiError;
```

```js
// error middleware using the class — bottom of app
app.use((err, req, res, next) => {
  const statusCode = err.statusCode || 500;
  res.status(statusCode).json({
    message: err.message,
    stack: err.stack,
  });
});
```

## 9. Router-Level Middleware

Same idea, but scoped to a route/router. Simplest form: add `next` to a route handler and run checks before continuing:

```js
app.get("/home", (req, res, next) => {
  // perform certain checks first
  if (!req.body.username) {
    return res.end("Not allowed"); // cycle terminated
  }
  next(); // otherwise continue to the next handler
}, (req, res) => {
  res.end("Welcome home");
});
```

Or with an `express.Router()`:

```js
import { Router } from "express";
const router = Router();

router.use((req, res, next) => {
  console.log("Router-level middleware");
  next();
});

router.get("/dashboard", (req, res) => res.end("Dashboard"));
app.use("/user", router);
```

## 10. Third-Party Middleware

Install from npm, `app.use()` them — no logic to write yourself. **But trust matters:** if the third-party package is vulnerable, your app is exposed (e.g., the Cloudflare outage that took down login systems relying on it, including ChatGPT's). Still, no company writes every middleware from scratch — some reliance on trusted third parties is unavoidable.

### 10.1 Helmet — overall protection (7 security policies)

Helmet secures HTTP headers: Content-Security-Policy, cross-origin policies (opener/resource/embedder), referrer policy, X-Content-Type-Options, DNS prefetch control, X-Download-Options, frame options, etc. — protection against XSS, clickjacking, content sniffing, and helps restrict things like content copying.

```bash
npm install helmet
```

```js
import helmet from "helmet";

app.use(helmet()); // one line = all default protections

// or configure individual policies with an object:
app.use(helmet({
  contentSecurityPolicy: {
    directives: { defaultSrc: ["'self'"] },
  },
  crossOriginResourcePolicy: { policy: "same-origin" },
  xDownloadOptions: false, // example: toggle a policy off
}));
```

> Without helmet you'd install and configure each policy library individually. Helmet = one-way traffic: one install, seven policies.

### 10.2 CORS — Cross-Origin Resource Sharing

- Frontend (origin A) calling a backend (origin B) with a **different IP/port/domain** triggers a CORS check during the **preflight** (TCP handshake — servers decide "can I trust this origin?").
- Neighbor analogy: a stranger from flat B brings you dinner — you verify before eating. Server verifies the origin before sharing data.
- Typical error: `Access to fetch at ... from origin ... has been blocked by CORS policy: response doesn't pass the access control check.`
- Same reason MongoDB Atlas rejects you when your Wi-Fi/IP changes — the new IP isn't a trusted origin.

```bash
npm install cors
```

```js
import cors from "cors";

app.use(cors());                 // allow ALL origins ("*")

// or restrict to a trusted origin:
app.use(cors({
  origin: "http://localhost:5173", // only this frontend may call the API
}));
```

### 10.3 Morgan — HTTP request logger

Replaces the hand-written logger middleware. Logs method, URL, status code, response time, response size (and with `combined`: IP, user-agent — laptop/Chrome/Linux etc.).

```bash
npm install morgan
```

```js
import morgan from "morgan";

app.use(morgan("dev"));      // concise, colored — development
// app.use(morgan("tiny"));     // minimal
// app.use(morgan("combined")); // Apache-style, most detail — production
```

Example `dev` output: `POST /login 200 12.345 ms - 25`

*(Related: **Winston** — another popular logging middleware/library.)*

### 10.4 Multer — multipart/form-data (file uploads)

- Express has **no built-in ability** to handle multimedia/**multipart form data** (forms containing images, PDFs, dropdowns, etc.).
- Multer is *"a Node.js middleware for handling multipart/form-data."*

```bash
npm install multer
```

**Basic usage (destination only):**

```js
import express from "express";
import multer from "multer";

const app = express();
app.use(express.json());
app.use(express.urlencoded({ extended: true }));

const upload = multer({ dest: "uploads/" }); // multer creates the folder

// three upload modes: .single(field) | .array(field) | .fields([...])
app.post("/profile", upload.single("dp"), (req, res) => {
  res.end("DP done");
});

app.listen(3000, () => console.log("Server running"));
```

Test in Postman: `POST /profile` → Body → **form-data** → key `dp` (type: File) → attach image.

**Problem:** the saved file has a random hashed name with **no extension** → appears corrupted/unreadable. Multer only manages the file; format preservation is on you.

**Fix — diskStorage with original filename:**

```js
const storage = multer.diskStorage({
  destination: (req, file, cb) => {
    cb(null, "uploads/");
  },
  filename: (req, file, cb) => {
    // keep original name → keeps the .png/.jpg extension → format preserved
    cb(null, file.originalname);
  },
});

const upload = multer({ storage });
```

> Note: the extension (`.png`) is what makes the file readable — you can rename the base name freely, but the extension must survive. Multer's default random naming exists to avoid collisions (a **buffer**-like lightweight storage approach — same idea as MongoDB storing images as keys/buffers, decoded back when displayed).

### 10.5 Nodemailer — sending emails (SMTP)

- Email uses **SMTP** (Simple Mail Transfer Protocol), not HTTP.
- Push notifications (OTP/WhatsApp-style) → services like **Twilio**; production email at scale → **AWS SES**; learning/small apps → **Nodemailer** (easy config, free with Gmail).
- Never use your real Gmail password. Generate a Google **App Password**: Gmail → Manage your Google Account → Security → search "App passwords" → verify → get a 16-char app password.

```bash
npm install nodemailer
```

```js
// nodemailer.js
import nodemailer from "nodemailer";

// 1. transporter — the "delivery guy"
const transporter = nodemailer.createTransport({
  service: "gmail",
  auth: {
    user: "youraddress@gmail.com",
    pass: "tdrf azmm trrb ezxx", // Google App Password (NOT your real password)
  },
});

// 2. mail options — what to send and to whom
const mailOptions = {
  from: "youraddress@gmail.com",
  to: "recipient@gmail.com",
  subject: "Welcome onboard!",
  text: "Hello Aryan",
};

// 3. send
transporter.sendMail(mailOptions, (error, info) => {
  if (error) console.log(error);
  else console.log("Mail sent successfully:", info.response);
});
```

## 11. API Fundamentals & Contracts

### What is an API?

> A medium through which two systems (A and B) communicate. Usually: medium = **HTTP protocol**, mode = **JSON**.

**Anatomy of an API URL:** `protocol + base domain + endpoint`
e.g., `https://gfg.com/web-development`

### API Contracts — "Contract first, API later"

Before A and B connect, both parties agree on rules (like signing an offer letter — salary, hours, notice period). Common contract rules:

1. **Respect the method** — GET to fetch, POST to create, PUT to update, DELETE to remove.
2. **Respect the status codes** — 201 for created, etc.
3. **Use nouns, not verbs** in endpoints:
    - ❌ `/getAllUsers`, `/updateMyUser`, `/deleteThisUser` (verbs = actions; the HTTP method already conveys the action)
    - ✅ `GET /users`, `GET /users/:id`, `PUT /users/:id`, `DELETE /users/:id`
    - Use **plural** nouns (`/users`, not `/user`).
4. **No camelCase in URLs — use hyphens**: ❌ `/getAllIphoneUsers` → ✅ `/iphone-users` (e.g., `gfg.com/web-development`).
5. **Respect the agreed data type** — if the server expects JSON, send JSON; if HTML is returned, there's a predefined schema for handling it.

### Gateway vs Endpoint, Reverse Proxy, Microservices (System Design Context)

- **API Gateway**: every request first passes through a gateway (e.g., `gfg.org`) which routes to internal services — it hides where services are actually hosted → acts as a **reverse proxy**.
- **Forward proxy** = hides the *client* (e.g., VPN). **Reverse proxy** = hides the *servers/services* (e.g., **NGINX**, load balancers L4/L7).
- **Microservices**: when a service (orders, payments, auth) outgrows a threshold, it becomes its own app with its own team, possibly its own language (Next.js UI + Django auth, etc.), connected via APIs. The empty container holding them (e.g., "GFG") is the **shell app**. Benefits: easier maintenance, easier debugging, freedom of tech stack.
- **Module Federation**: service B exposes its functionality to service A temporarily **without leaking its code** — e.g., Razorpay lends you `createOrder`/`processOrder` via an **API key** (their exposed public/private key) for the duration of the payment; you never see or own their code.

## 12. Quick Revision

**Middleware** = functions with access to (1) `req`, (2) `res`, (3) `next`, that can:

1. execute any code,
2. modify request/response,
3. end the request–response cycle,
4. call the next middleware via `next()`.

**Five types:** application-level, router-level, error-handling (bottom of app, `(err, req, res, next)`), built-in (`express.json`, `express.urlencoded`), third-party (`helmet`, `cors`, `morgan`, `multer`, `nodemailer`).

**Placement:** all middleware above routes; error middleware below routes. Forgetting `next()` = orphan/hanging request. Stacking = **middleware chaining** (like promise chaining, scope chaining).

**Common third-party map:**

| Package | Job |
|---|---|
| `helmet` | 7 security header policies in one line |
| `cors` | Configure trusted cross-origin access |
| `morgan` / `winston` | Request logging (`dev` / `tiny` / `combined`) |
| `multer` | Multipart form-data / file uploads |
| `nodemailer` | Email over SMTP (Gmail app password) |
| `cookie-parser`, `body-parser` | Parse cookies / bodies |
| `nodemon` | Dev auto-restart (not middleware, but essential tooling) |
