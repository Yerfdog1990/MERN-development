# Using CORS in Node.js

## 1. The Problem: The CORS Error

You call an API from your website with `fetch()` and the console shows red text:

- *"No 'Access-Control-Allow-Origin' header is present on the requested resource"*, or
- *"The 'Access-Control-Allow-Origin' header has a value `<some_url>` that is not equal to the supplied origin"*

**Key insight: this is not a bug — it's expected behavior.** Browsers enforce the **same-origin policy**, which blocks resource sharing across different origins. **CORS (Cross-Origin Resource Sharing)** is the mechanism to deliberately relax that restriction. (10,000+ StackOverflow questions under the `cors` tag — it hits frontend and backend devs alike.)

---

## 2. The Same-Origin Policy

> The web's version of "don't talk to strangers," enforced by the browser.

All modern browsers restrict how `XMLHttpRequest` and `fetch` requests from one origin interact with resources from another origin.

**An origin = scheme + domain + port.** All three must match for two URLs to be "same-origin."

With origin `http://localhost:3000`:

| URL | Type | Reason |
|---|---|---|
| `http://localhost:3000/about` | Same-origin | Path is **not** part of the origin |
| `http://localhost:3000/shop/product.html` | Same-origin | Path is not part of the origin |
| `http://localhost:5000` | Cross-origin | Different **port** |
| `https://localhost:3000` | Cross-origin | Different **scheme** (HTTPS vs HTTP) |
| `https://blog.logrocket.com` | Cross-origin | Different scheme, domain, and port |

Important consequences:

- Your SPA frontend on `http://localhost:3000` **cannot** call your API on `http://localhost:5000` without CORS.
- `https://mywebsite.com` → `https://api.mywebsite.com` is **still cross-origin** — subdomains count as different origins.
- The browser blocks the **response from being shared with the client** (the request may actually reach the server). Good for security (cross-site forgery protection), but legitimate cross-origin needs are everywhere — especially in **microservice architectures** where apps live on different origins.

---

## 3. What CORS Is

> CORS is an **HTTP header-based protocol** that enables resource sharing between different origins. The **server** decides, via response headers, which origins/methods/headers it trusts; the **browser** enforces the decision. For non-simple requests it also relies on a **preflight** `OPTIONS` request.

### The CORS response headers

```http
Access-Control-Allow-Origin: <allowed_origin> | *
Access-Control-Allow-Methods: <method> | [<method>]
Access-Control-Allow-Headers: <header> | [<header>]
Access-Control-Max-Age: <delta-seconds>
```

**`Access-Control-Allow-Origin`** — the most important one:

- Lists origin(s) allowed to access the resource. If absent → CORS isn't set up on the server at all.
- The browser compares it to the request's `Origin` header. Match → resource shared; mismatch → CORS error.
- `*` = allow all origins (public APIs); a full origin like `https://mywebsite.com` = restrict to that client.

**`Access-Control-Allow-Methods`** — which HTTP methods (GET, POST, PUT, ...) the server accepts cross-origin. Sent in preflight responses. A method not on the list → CORS error. Useful to stop cross-origin POST/PUT/PATCH/DELETE mutations.

**`Access-Control-Allow-Headers`** — which request headers are permitted (e.g., custom ones like `x-auth-token`). Also a preflight response header; unlisted headers → CORS error.

**`Access-Control-Max-Age`** — lets the browser **cache the preflight result** for N seconds, so it doesn't pay the extra `OPTIONS` round-trip on every request.

---

## 4. Simple Requests vs. Preflighted Requests

**Simple requests** skip the preflight. A request is "simple" only if ALL of these hold:

1. Method is `GET`, `POST`, or `HEAD`
2. Only CORS-safelisted headers are set manually (`Accept`, `Accept-Language`, `Content-Language`, `Content-Type`) besides user-agent headers
3. `Content-Type` is one of: `application/x-www-form-urlencoded`, `multipart/form-data`, `text/plain`
4. No event listeners on `XMLHttpRequest.upload`
5. No `ReadableStream` in the request

Fail any condition (e.g., `Content-Type: application/json`, an `Authorization` header, a `DELETE` method) → the request is **preflighted**:

```text
Browser                          Server
   |---- OPTIONS /api/data ------->|   (preflight: "is the real request safe?")
   |<--- Allow-Origin/Methods/... -|
   |                               |
   |---- actual request ---------->|   (only if preflight headers match)
   |<--- response + CORS headers --|
```

If the preflight response headers don't match what the main request needs, the main request is **never sent**.

## 5. Enabling CORS in Node.js/Express (You Control the Backend)

CORS is just headers — you can set them manually in any language/framework, or use the `cors` middleware in Express:

```bash
npm install cors
```

### Minimal setup

```js
const express = require("express");
const cors = require("cors");

const app = express();
app.use(cors()); // enable CORS with defaults

app.get("/", (req, res) => {
  res.send("API running with CORS enabled");
});

app.listen(5000, () => console.log("Server running on port 5000"));
```

### Default configuration (when you pass no options)

```json
{
  "origin": "*",
  "methods": "GET,HEAD,PUT,PATCH,POST,DELETE",
  "preflightContinue": false,
  "optionsSuccessStatus": 204
}
```

### Restrictive production-style config

Only GET from one site, two allowed headers, 10-minute preflight cache:

```js
app.use(cors({
  origin: "https://yourwebsite.com",
  methods: ["GET"],
  allowedHeaders: ["Content-Type", "Authorization"],
  maxAge: 600, // seconds
}));
```

## 6. Full Demo — Four Configuration Patterns

```js
/**
 * CORS Middleware Demo
 * Frontend on origin A calling backend on origin B triggers a CORS check.
 * Install: npm install cors
 */
import express from "express";
import cors from "cors";

const app = express();
app.use(express.json());

// ── Option 1: allow ALL origins ─────────────────────────────────────
// Sets Access-Control-Allow-Origin: * — fine for dev, NOT for production
app.use(cors());

// ── Option 2: single trusted origin ─────────────────────────────────
// app.use(cors({
//   origin: "http://localhost:5173", // only this frontend may call the API
// }));

// ── Option 3: multiple origins via callback function ────────────────
// const allowedOrigins = [
//   "http://localhost:5173",
//   "https://your-frontend.com",
//   "https://staging.your-frontend.com",
// ];
//
// app.use(cors({
//   origin: (origin, callback) => {
//     // Allow requests with NO origin (mobile apps, curl, Postman)
//     if (!origin) return callback(null, true);
//
//     if (allowedOrigins.includes(origin)) {
//       callback(null, true);                  // allowed
//     } else {
//       callback(new Error("Not allowed by CORS")); // blocked
//     }
//   },
// }));

// ── Option 4: full flexible config ──────────────────────────────────
// app.use(cors({
//   origin: ["http://localhost:5173", "https://your-frontend.com"], // array also works
//   methods: ["GET", "POST", "PUT", "DELETE"],       // allowed HTTP methods
//   allowedHeaders: ["Content-Type", "Authorization"], // allowed request headers
//   credentials: true,  // allow cookies + auth headers cross-origin
//   maxAge: 86400,      // cache preflight for 24h (seconds)
// }));

// ── Sample routes ────────────────────────────────────────────────────
app.get("/", (req, res) => {
  res.json({
    message: "CORS is configured!",
    info: "This API can be accessed from allowed origins",
  });
});

app.get("/api/data", (req, res) => {
  res.json({ data: "Public data accessible via CORS" });
});

const username = "Yerf";
const password = "Yerf123";

app.post("/api/login", (req, res) => {
  if (req.body.username === username && req.body.password === password) {
    return res.json({ message: "Login endpoint - POST request allowed" });
  }
  return res.status(401).json({ error: "Invalid credentials" });
});

const PORT = 3001;
app.listen(PORT, () => {
  console.log(`CORS demo server running on http://localhost:${PORT}`);
});
```

### Notes on the options

- **`origin`** accepts a string, an **array** of origins, a **RegExp**, or a **function** `(origin, callback)` for dynamic whitelisting (Option 3). The function form is the standard pattern for multi-environment apps (local + staging + prod).
- **Requests with no `Origin` header** (curl, Postman, mobile apps, server-to-server) bypass browser CORS entirely — the `if (!origin) return callback(null, true)` line accommodates them. Remember: **CORS is browser-enforced only; it is not server-side security.** Anyone can still curl your API — you still need auth.
- **`credentials: true`** sends `Access-Control-Allow-Credentials: true`, needed when the frontend uses cookies/sessions or sends `Authorization` with `fetch(..., { credentials: "include" })`. **Gotcha:** with credentials, `origin` **cannot** be `*` — you must specify explicit origin(s).
- **`maxAge`** maps to `Access-Control-Max-Age` (preflight caching).
- Register `app.use(cors())` **before your routes** (standard middleware placement) so preflights and headers apply to all of them.

## 7. When You Only Control the Frontend

You can't add headers to responses from a server you don't own (e.g., a public API). Workaround: route requests through a **CORS proxy** — a reverse proxy that adds the CORS headers to the proxied response (e.g., the `cors-anywhere` Node.js project; you can deploy your own instance).

```js
// direct (blocked):
fetch("https://jsonplaceholder.typicode.com/posts");

// via proxy (proxy adds the CORS headers):
fetch("https://cors-anywhere.herokuapp.com/https://jsonplaceholder.typicode.com/posts");
```

> Prefer deploying your own proxy — public instances are rate-limited/unreliable, and you're routing your traffic through a third party.

---

## 8. Quick Revision

- **Same-origin policy**: browser blocks cross-origin resource sharing; origin = scheme + domain + port (path excluded, subdomains count as different).
- **CORS**: header-based protocol letting the *server* opt in to cross-origin sharing; *browser* enforces it.
- **Key headers**: `Access-Control-Allow-Origin` (who), `-Allow-Methods` (which verbs), `-Allow-Headers` (which headers), `-Max-Age` (preflight cache), `-Allow-Credentials` (cookies/auth).
- **Simple vs preflighted**: GET/POST/HEAD with safelisted headers and form/text content types skip preflight; everything else (e.g., JSON POSTs with `Authorization`) triggers an `OPTIONS` preflight first.
- **Express**: `npm i cors` → `app.use(cors(options))`; origin as string/array/regex/function; `credentials: true` requires explicit origins (no `*`).
- **CORS ≠ security**: it protects browser users from malicious sites, not your API from attackers — non-browser clients ignore it entirely.
- **No backend access?** Use a CORS proxy (`cors-anywhere` style).
